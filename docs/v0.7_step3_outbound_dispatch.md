# v0.7 Step 3 — Outbound dispatch

Step 3 turns confirmed automatic order operations into durable asynchronous
provider commands. It deliberately excludes provider webhooks and Inbox
processing, which are Step 4 responsibilities.

## Flow

```text
LangGraph confirmation
  -> resolve tenant + order_operation connection
  -> queued operation + audit events + Outbox command (one transaction)
  -> standalone Outbox worker
  -> bounded concurrent connection gates + canonical HTTP transport
  -> aggregate/event + delivery attempt + Outbox finalization (one transaction)
```

Delivery investigations use the corresponding `support_case` aggregate. A
new investigation writes its case, creation event, and command atomically.
For a reused investigation the same transaction appends the trigger and first
checks for a command already associated with that case: historical cases with
no command receive one, while an existing command is never duplicated.

## Configuration

`PROVIDER_CONNECTIONS_JSON` is parsed once when the API or worker starts. It
is an array of connections containing `connection_id`, `tenant_id`,
`capability`, `base_url`, `endpoint`, `authentication`, optional `timeout`,
`max_concurrency`, and `requests_per_second`. Persisted commands resolve by
the exact `(connection_id, provider_capability)` pair; capabilities that share
an ID must share identical transport settings and share one execution gate.
See `.env.example` for a
non-working safe placeholder.

HTTPS is required by default. Local simulator use may explicitly set
`PROVIDER_ALLOW_INSECURE_HTTP=true`; it must never be enabled dynamically per
request. The worker starts independently:

```powershell
python -m agent.integrations.worker_main
```

The worker does not start FastAPI, LangGraph, or demo identity authentication.

If a confirmed automatic operation cannot resolve its configured connection,
the Graph calls the provider-failure application coordinator. In one PostgreSQL
transaction it moves the operation to `manual_review`, creates or reuses a P1
`order_operation_review`, records confirmation/status/case-attachment events,
and never creates an Outbox row. Only explicit connection-not-found or
configuration-unavailable errors take this fallback; database and programming
errors continue to surface normally.

## Result handling

- Accepted operation: `queued -> submitted`, one status event, attempt
  `accepted`, Outbox `published`.
- Explicit provider rejection: operation `rejected`, attempt
  `provider_rejected`, Outbox `dead`, no technical case; validated provider
  operation IDs and references are retained in the attempt and domain event.
- Retryable network/timeout/408/429/5xx failures: operation stays `queued`;
  retry policy writes `retry_scheduled` with the existing capped exponential
  backoff and `Retry-After` support.
- Terminal technical failure: operation becomes `manual_review`; an
  `order_operation_review` P1 case with `provider_delivery_failed` is created
  or reused and linked atomically; attempt and Outbox become terminal. Unknown
  exceptions are persisted only through fixed safe error codes/messages.
- Delivery investigations remain unresolved. Provider updates are appended as
  `provider_update` events; technical failure adds `provider_delivery_failed`
  to the existing case rather than creating a duplicate investigation.

All finalization writes are fenced by command, lease, worker, and attempt
identity. A stale worker cannot complete a lease reclaimed by another worker.
If a lease renewal loses its fence, the outstanding gate wait or HTTP task is
cancelled and no finalizer runs.

## Operational limits

Each claimed batch is scheduled concurrently, bounded by `batch_size`.
`ConnectionGateRegistry` uses one semaphore and one monotonic-clock rate gate
per `connection_id` *inside one process*. Capabilities sharing an ID share the
same limit. This is intentionally not a distributed global rate limit; a
future Redis or gateway implementation can replace the gate without changing
Graph, service, or provider wire contracts.

`create_provider_simulator()` is a demo-only FastAPI application. It validates
canonical envelopes and idempotency headers and can deterministically return
accepted, rejected, 409/422, 429 with Retry-After, 500, timeout, invalid JSON,
or a wrong command ID. It is never mounted by the production API.

## Compatibility with Step 4

`OrderCommandAdapter` / synchronous submission remains transitional only for
v0.6 compatibility. The formal Graph path queues commands and never performs
HTTP submission directly. Step 4 now provides the HMAC-authenticated webhook
route and standalone Inbox worker. Every claimed callback is revalidated
against its persisted canonical Outbox and local aggregate before any domain
write. See `docs/v0.7_step4_webhook_inbox.md` for the trust boundary,
finalization rules, process topology, and remaining operational limits.
