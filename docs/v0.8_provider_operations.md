# v0.8 Provider operations control plane

## Objective

v0.8 adds a tenant-scoped, auditable recovery surface for Provider Outbox and
Inbox failures. It lets an authenticated Supervisor inspect safe operational
metadata and start an eligible recovery cycle without exposing Provider
credentials, callback or command payloads, customer/order content, raw error
messages, SQL details, or cross-tenant resource existence.

The control plane does not call a Provider or run a Worker synchronously. A
redrive commits database state and immutable audit records; the existing
Outbox or Inbox Worker later claims the new cycle through its ordinary fenced
path.

## Architecture and flow

```text
authenticated internal HTTP request
  -> require_access_scope
  -> ProviderOperationsService authorization
  -> tenant-scoped PostgresProviderOperationsRepository transaction
  -> strict response DTO

Outbox redrive transaction
  -> lock Outbox + terminal attempt + associated aggregate/case
  -> validate technical-failure eligibility
  -> coordinate aggregate and case audit changes
  -> append immutable redrive audit and open delivery cycle
  -> ordinary Outbox Worker claim and finalization

Inbox redrive transaction
  -> lock failed Inbox row
  -> append immutable redrive audit and open processing cycle
  -> ordinary Inbox Worker claim
  -> canonical association, ordering, and fencing checks
  -> domain finalization
```

The FastAPI lifespan creates the Provider operations repository and service
from the application-owned PostgreSQL pool. Provider Ops adds no new Provider
credential dependency and does not create another pool or start either Worker;
the wider API lifespan may still load the existing Provider connection
resolvers used by the v0.7 messaging routes.

## HTTP routes

All routes are under `/internal/provider-operations`:

| Method | Route | Result |
| --- | --- | --- |
| `GET` | `/queues` | Tenant Outbox/Inbox counts and oldest due timestamps |
| `GET` | `/outbox/{command_id}` | Safe Outbox status, attempts, and redrive history |
| `GET` | `/inbox/{inbox_id}` | Safe Inbox status, attempts, and redrive history |
| `POST` | `/outbox/{command_id}/redrives` | One atomic Outbox recovery cycle |
| `POST` | `/inbox/{inbox_id}/redrives` | One atomic Inbox processing cycle |

Detail history is bounded by `history_limit` (`1..100`, default `50`). Tenant
identity is derived only from the authenticated access scope and is never a
query or body parameter. The redrive body contains only:

```json
{
  "request_id": "ops:incident-2026-08-19",
  "reason_code": "transient_incident_resolved"
}
```

The fixed reason codes are:

- `dependency_or_configuration_restored`
- `transient_incident_resolved`
- `manual_retry_approved`

Free-form reasons and extra request fields are rejected.

## Authorization and non-disclosure

Reads require the exact `supervisor` role plus `provider_ops:read`; redrives
require the exact `supervisor` role plus `provider_ops:redrive`. The Service
and PostgreSQL repository independently enforce both checks. A forged role or
permission set fails closed.

Missing credentials on a structurally valid request use the shared `401`
behavior. Permission failures are
`403`. Missing and cross-tenant identifiers return the same fixed `404`
envelope. Eligibility, request-id, audit, aggregate-state, and concurrency
conflicts are fixed allowlisted `409` responses; an unknown internal conflict
becomes the generic `provider_operations_conflict`. Storage failures are a
fixed `503`. Provider-path/body validation failures, including malformed JSON
from an authenticated caller, use a sanitized `422` and do not echo supplied
values.

Response DTOs are strict field whitelists. They may expose stable command,
Inbox and aggregate UUIDs; aggregate type; queue/status; cycle and attempt
counts; timestamps; safe failure kind/error code/HTTP status; attempt outcome;
and immutable redrive request, actor, reason code and cycle metadata. They do
not expose:

- command or callback payloads, raw-body hashes, signatures, or secrets;
- idempotency keys, customer/order/source-message content;
- Provider connection identifiers/settings or Provider operation/reference;
- worker leases/identifiers, free-form diagnostic text, exceptions,
  constraint names, or SQL.

## Recovery semantics

### Outbox

Only a `dead`, unleased Outbox row with current-cycle terminal technical
evidence is eligible. A terminal technical failure or the attempt-exhausting
lease-expired outcome is accepted. Explicit Provider business rejection is
never redrivable. Other states, active leases, stale/missing terminal evidence,
and non-exhausting lease expiry are rejected.

An Order Operation recovery atomically requires `manual_review` with its valid
review-case link, appends Operation and Case audit events, changes the Operation
to `queued`, clears manual-review linkage, opens a `retry_scheduled` Outbox
delivery cycle, and writes the redrive audit. The linked Case remains open with
its priority, assignment, status, and version unchanged.

A Support Case Outbox recovery validates the command/case association, appends
a Provider-redrive Case audit, and opens the Outbox cycle. It does not change,
close, reprioritize, or reassign the Case.

### Inbox

Only a `failed`, unleased Inbox row is eligible. Redrive changes it to
`received`, increments `processing_cycle`, resets only `attempts_in_cycle`, and
clears failure/lease state. Lifetime `processing_attempts` and every original
callback, payload, hash, event, command and aggregate association remain
unchanged. The ordinary Worker must reclaim the row and repeat the complete
canonical association, ordering and fencing validation; the API provides no
bypass.

## Idempotency, concurrency, and audit

`request_id` is unique per tenant and queue kind: Outbox and Inbox have separate
namespaces. Replaying the same tenant/queue/request, target, and fixed reason
returns the original immutable audit even after later Worker state transitions.
Reusing it for another target or reason within that queue is a conflict. The
same identifier may independently name one Outbox and one Inbox recovery.
Database uniqueness is the race backstop: concurrent identical requests
converge on one audit, while different requests racing on one target yield one
recovery and one eligibility/state conflict.

The current implementation records fixed reason codes and authenticated actor
identity. Legacy v0.7 Outbox redrive rows retain their original free-form
database values. They expose `reason_code: null`, and a request id that does not
meet the v0.8 allowlist is exposed as `request_id: null`; neither legacy text
value is projected by this API.

## Migration 0008 and data impact

Migration `0008_provider_operations.sql` is additive:

- adds nullable `outbox_redrives.reason_code` and history indexes, preserving
  all legacy rows without relabeling them;
- adds Inbox `processing_cycle` and `attempts_in_cycle`, backfilling existing
  Inbox messages and attempts as cycle 1 while retaining lifetime attempt
  totals;
- creates immutable, tenant/request-id-unique `inbox_redrives`;
- adds the constrained `provider_redrive` Support Case event reason field/type
  and audit-history index.

The migration does not rewrite callback payloads/hashes or Outbox command
payloads. Apply it before starting the v0.8 API or Workers. Migration files are
immutable after application.

## Deployment and process impact

The Compose topology is unchanged: migrations run first, then the API and the
separate Outbox/Inbox Workers. The API image is version `0.8.0`; the Worker
processes still need their existing database/configuration boundaries. The
control-plane API must remain behind an internal gateway and must not be made
public solely because Compose binds the application to loopback.

`DemoIdentityProvider` is deterministic local-development infrastructure, not
production authentication. Production deployment is not approved by v0.8 and
requires replacement with the organization's OAuth/OIDC/SSO identity boundary,
gateway controls, identity lifecycle and operational review.

### Runtime image security and provenance

The final application image is based on the immutable official stable manifest
`langchain/langgraph-api:0.12.6-py3.11-wolfi@sha256:60a141df7699eb28a6fd4e09cdf3e81d8e61ef7a6d9b17769af433100ab18ee0`.
Its Datadog helper is rebuilt from public Datadog Agent 7.81.2 source commit
`6dbfeceb7c8e1575803f209afaa62004293724d6` using
`golang:1.26.6-bookworm@sha256:116d58cbd88c1297624acc6e967a060012422bacf9930927e23fb719189c6f36`.
That glibc builder is required for ABI parity with the flattened Wolfi runtime;
the build asserts its pinned GCC 12.2.0, Git 2.39.5, glibc-dev 2.36 and
binutils 2.40 packages, verifies the ELF interpreter and shared libraries, and
executes the helper in the final runtime as a build gate.
The build retains `CGO_ENABLED=1`, the upstream
`serverless,otlp,zlib,zstd` tags, the 7.81.2/1.10.2 linker metadata, and the
original `/app/datadog-init ... ddtrace-run ...` entrypoint semantics. Source,
Git, compiler and module caches remain in the discarded builder stage. The
Apache-2.0 license, NOTICE, and upstream third-party license inventory are
included in `/usr/share/licenses/datadog-init/`.

The builder applies two explicit security-fixed module overrides, verified by
Go's module checksum mechanism: `golang.org/x/net@v0.56.0` and
`google.golang.org/grpc@v1.82.1`. Both are deliberate additional divergences
from the public 7.81.2 graph.

The build verifies the exact upstream vulnerable-helper checksum, removes only
that path, copies the sanitized upstream root filesystem into a scratch-based
stage, and explicitly reconstructs the pinned image configuration before
adding application layers. This flattening is required because layer-aware
scanners can otherwise report an overwritten ancestor binary even though it is
not reachable in the final filesystem. File ownership/modes, entrypoints,
healthcheck, environment, workdir and runtime labels are parity-checked. The
tradeoff is that the final OCI ancestry no longer contains the original base
layers; provenance relies on the immutable upstream digest, checksum gate, and
recorded parity evidence. The reconstructed OCI metadata names the pinned
LangGraph manifest as its direct base rather than retaining the inner
Chainguard base label. Upstream licenses/notices remain in the copied rootfs.

This is not a byte-for-byte rebuild of the helper originally copied into the
LangGraph image. That binary reported a modified dependency graph whose cited
source revision was not publicly retrievable, and the official image exposed
no verifiable provenance/SBOM attestation. The user approved the public release
source graph as the explicit compatibility tradeoff needed to remove the Go
1.26.5 runtime vulnerabilities. The final image separately constrains
`cryptography` to `>=50,<51` under `/api/constraints.txt`.

Treat every change to the two image digests, source commit, build tags, linker
metadata, pinned builder packages, module overrides, or cryptography range as
a security-sensitive runtime upgrade. Pull
and inspect the candidate, rebuild without a stale final base, run API and both
Worker smoke checks, audit the final filesystem/licenses, and require a fresh
Critical/High vulnerability scan. Upstream publication of an attested patched
stable binary should trigger review of replacing this source-build exception.

## Validation

Static and non-database checks:

```bash
uv sync --frozen --extra dev
uv run ruff check .
uv run mypy src
uv run pytest -m "not postgres" -p no:cacheprovider
uv build
docker compose config --quiet
```

Run the PostgreSQL suite only against an explicitly disposable database:

```bash
CASE_TEST_POSTGRES_URI=postgresql://test-user:test-password@127.0.0.1:55432/test-db \
  uv run pytest -m postgres -p no:cacheprovider
```

Never point `CASE_TEST_POSTGRES_URI` at production. Cross-component acceptance
is in `tests/integration_tests/test_postgres_provider_operations_e2e.py` and
uses in-process HTTP plus real repositories/Workers/Finalizers with a fake
network-free Provider transport.

## Limitations and rollback considerations

v0.8 intentionally has no management UI, retention cleanup, Worker heartbeat
or Prometheus metrics, distributed limiter/external queue, or dynamic key
rotation. It does not change the LangGraph workflow or Provider wire schema.

Migration `0008` must be applied before any v0.8 API or Worker starts. During a
rolling upgrade, stop or drain every v0.7 Inbox Worker, apply `0008`, and then
start only v0.8 Inbox Workers before enabling redrive routes. A v0.7 Inbox
Worker is not compatible with cycle-aware/redriven Inbox data and must never
run after a v0.8 Inbox recovery has occurred.

Rollback may disable the five routes while keeping v0.8 Workers and migration
`0008`. Rolling the Inbox Worker back to v0.7 requires a separately reviewed
data-coordination gate proving that no cycle greater than one or v0.8 redrive
state exists; otherwise it is prohibited. Preserve audit rows and cycles,
verify no recovery is in flight, and use a reviewed forward migration for any
schema removal rather than editing or reversing an applied migration.
