# v0.5 Business Rules Draft

Status: **Implemented and validated for the v0.5.0 release**

Target release: `v0.5.0`
Scope of this document: business rules and state matrices only. No production
code, database migration, or LangGraph workflow change is implemented by this
document.

## 1. Goal and scope

v0.5 expands the assistant from refund, order inquiry, complaint, and handoff
handling into four additional customer-service capabilities:

1. order cancellation;
2. return and exchange requests;
3. delivery-issue reporting;
4. customer-visible support-case status inquiry.

The existing v0.4 risk, complaint, refund, and handoff policies remain in force.
In particular, safety processing still has priority over ordinary business
operations, and deterministic business policies—not LLM prose—decide whether an
operation is allowed.

### Non-goals for v0.5

- authentication and authorization;
- verifying that an order belongs to the current user;
- connecting to a real OMS, WMS, carrier, inventory, payment, or CRM platform;
- an agent-facing operations UI;
- SLA timers, notifications, or automatic escalation jobs;
- allowing an LLM to directly mutate an order or decide eligibility.

These exclusions mean v0.5 remains a demonstration system. Its internal APIs
must not be exposed to untrusted users or real customer data.

## 2. Shared decision principles

### 2.1 Structured facts and deterministic decisions

An LLM may identify intent, extract a reason, or classify free text. It must not
decide cancellation, return, exchange, delivery, or visibility policy. Domain
policy receives validated structured facts and returns a structured decision.

### 2.2 Read before write

Every operation follows this order:

```text
identify order -> load current order -> evaluate policy -> explain result
-> obtain confirmation when required -> submit idempotent operation
```

The system must evaluate policy again after confirmation because order state may
have changed while the graph was interrupted.

### 2.3 Confirmation boundary

Cancellation, return, and exchange are state-changing operations. Any request
that will be submitted—automatically or for manual review—must pause for one
explicit confirmation. A rejected request, an already-completed idempotent
request and a status inquiry do not require a mutation confirmation. Reporting
a delivery issue does not itself require confirmation, but creating a
`delivery_investigation` support case requires one explicit confirmation.

Confirmation is scoped to one operation and one order. A confirmation from an
earlier turn cannot authorize a later operation or a different order.

### 2.4 Idempotency and concurrency

Each submitted operation needs a stable idempotency key derived from the thread,
source message, order, and operation type. Replaying the same request must return
the existing result rather than create a second operation. The Provider must
also detect a stale order version and require policy to be re-evaluated.

### 2.5 One primary business operation per turn

A triggering message may contain several observations and complaint reasons,
but it may submit at most one primary order operation. If the user requests
mutually exclusive operations for the same order—for example, both cancellation
and exchange—the assistant asks the user to choose and performs neither.

All case-creation reasons continue to be retained under the v0.4 rule that one
message creates at most one primary support case.

### 2.6 Existing safety and handoff behavior

- hard-critical risk continues to bypass normal business processing;
- semantic high or critical risk continues to use the existing risk response;
- low or medium risk combined with an actionable order request continues to use
  an explicit priority choice;
- confirmed human requests and formal complaints continue to use v0.4 policy;
- ordinary dissatisfaction alone does not create a support case.

## 3. Required order snapshot contract

The current demonstration data exposes only `shipped` and `delivered` examples.
It also combines order, delivery, payment, and refund facts. v0.5 policy needs a
clearer read-only order snapshot from the future Provider boundary.

Recommended minimum fields:

| Field | Purpose |
| --- | --- |
| `order_id` | Stable order identifier |
| `version` | Optimistic concurrency token |
| `order_status` | Commercial order lifecycle |
| `payment_status` | Payment/refund lifecycle, separate from order status |
| `fulfillment_status` | Warehouse/delivery lifecycle |
| `amount` | Monetary policy and manual-review threshold |
| `currency` | Prevent ambiguous monetary decisions |
| `created_at` | Order age and audit context |
| `shipped_at` | Cancellation and delivery context |
| `delivered_at` | Return-window calculation |
| `promised_delivery_at` | Deterministic delay calculation |
| `last_tracking_event_at` | Stalled-tracking calculation |
| `return_eligible` | Product/catalog restriction supplied by the order system |
| `exchange_eligible` | Product/catalog restriction supplied by the order system |
| `active_operation` | Existing cancellation/return/exchange request, if any |

Recommended independent statuses:

```text
order_status:       pending_payment | confirmed | cancelled | completed
payment_status:     unpaid | paid | refund_pending | partially_refunded | refunded
fulfillment_status: unfulfilled | processing | shipped | delivered
```

Separating these dimensions avoids invalid states such as treating `refunded`
as both a payment state and a shipping state.

## 4. Order cancellation policy

### 4.1 State matrix

| Current facts | Decision | Confirmation | Case |
| --- | --- | --- | --- |
| `pending_payment` + `unfulfilled` | Allow automatic cancellation | Yes | None |
| `confirmed` + `unfulfilled` | Allow cancellation; payment reversal is part of the provider operation | Yes | None |
| fulfillment `processing` | Do not auto-cancel; submit manual cancellation review | Yes | `order_operation_review`, `p1` |
| fulfillment `shipped` | Reject cancellation; offer delivery help or return after delivery | No | None unless another handoff reason exists |
| fulfillment `delivered` | Reject cancellation; offer return/exchange evaluation | No | None unless another handoff reason exists |
| order already `cancelled` | Return the existing result as an idempotent success | No | None |
| payment already `refund_pending` or `refunded` | Do not create a second refund action | No | None |
| state is missing, contradictory, or stale | Do not mutate automatically; submit manual review after confirmation | Yes | `order_operation_review`, `p1` |

### 4.2 Cancellation reason

The user may optionally provide a reason. Recommended normalized reason codes:

```text
ordered_by_mistake
no_longer_needed
incorrect_item_or_quantity
delivery_too_slow
payment_issue
other
```

The reason is recorded for audit and analytics but does not change cancellation
eligibility in v0.5.

### 4.3 Result semantics

`submitted` means the Provider accepted the operation, not that every downstream
payment or warehouse action has completed. Responses must distinguish:

- cancelled immediately;
- accepted and processing;
- awaiting manual review;
- rejected with an alternative next step.

## 5. Return and exchange policy

### 5.1 Shared eligibility

The recommended v0.5 baseline is:

- fulfillment must be `delivered`;
- `delivered_at` must be valid and no more than 7 calendar days ago;
- the product-specific Provider flag for the requested operation must be true;
- the order must not already be fully refunded;
- no unresolved duplicate operation of the same type may exist.

Returns and exchanges use an approved seven-calendar-day window starting at the
delivery timestamp. The request remains eligible through exactly
`delivered_at + 7 days`; it expires only after that instant. Product exclusions
must come from the Provider; the LLM must not infer whether a product is
returnable.

### 5.2 Return matrix

| Condition | Decision | Confirmation | Case |
| --- | --- | --- | --- |
| All shared rules pass and amount `< 100` | Submit return request | Yes | None |
| All shared rules pass and amount meets the configured manual-review threshold | Manual review | Yes | `order_operation_review`, `p1` |
| Not delivered | Reject; route to relevant delivery assistance | No | Depends on delivery policy |
| More than 7 calendar days after delivery | Reject under standard policy | No | None; confirmed human request may still create its existing case |
| Product is not return-eligible | Reject with a readable reason from structured provider data | No | None |
| Same return already unresolved/completed | Return existing operation | No | None |
| Missing or contradictory facts | Manual review | Yes | `order_operation_review`, `p1` |

### 5.3 Exchange matrix

Exchange requires inventory and variant availability, so eligibility cannot be
derived from text alone.

| Condition | Decision | Confirmation | Case |
| --- | --- | --- | --- |
| Shared rules pass and requested replacement is available | Submit exchange | Yes | None |
| Replacement availability is unknown | Manual review | Yes | `order_operation_review`, `p2` |
| Requested replacement is unavailable | Reject exchange; offer return evaluation | No | None |
| Same exchange already unresolved/completed | Return existing operation | No | None |
| Missing or contradictory facts | Manual review | Yes | `order_operation_review`, `p1` |

### 5.4 Normalized return/exchange reasons

```text
changed_mind
wrong_item_received
damaged_item
defective_item
missing_parts
not_as_described
size_or_variant_issue
other
```

`wrong_item_received`, `damaged_item`, `defective_item`, and `missing_parts` are
claims, not automatically verified facts. v0.5 may record the claim and request
evidence, but it must not state that the merchant or carrier is at fault.

### 5.5 Relationship with the existing refund flow

A return request represents the merchandise workflow; it does not independently
issue money at submission time. Any refund caused by a completed return must be
performed once by the downstream Provider after receipt/inspection, or linked
to the existing refund operation by a stable provider reference.

If an active refund, return, or exchange would cause a second financial outcome
for the same order or line item, policy must reject the new automatic operation
and return the existing operation or request manual review. The current v0.4
refund flow remains unchanged during v0.5 domain development, but phase two must
model this mutual-exclusion rule explicitly.

## 6. Delivery-issue policy

### 6.1 Supported issue types

```text
delayed
tracking_stalled
delivery_failed
marked_delivered_not_received
package_damaged
wrong_item_or_missing_parts
other_delivery_issue
```

### 6.2 Deterministic facts versus user claims

- `delayed` is supported when current time is later than
  `promised_delivery_at` and fulfillment is not `delivered`.
- `tracking_stalled` is supported when a shipped order has no tracking event for
  at least 72 hours.
- the remaining issue types originate as user claims and must be recorded as
  such until a Provider or human investigation verifies them.
- wording such as “lost” must not be presented as a verified carrier failure
  solely because the user used that word.

### 6.3 Delivery decision matrix

| Issue | Self-service response | Case |
| --- | --- | --- |
| Delay before promised time | Explain current status; no incident is asserted | None |
| Verified delay after promised time | Provide tracking facts and next step | `delivery_investigation`, `p2` only if the user asks for investigation or no usable tracking exists |
| Tracking stalled for at least 72 hours | Start investigation | `delivery_investigation`, `p1` |
| Delivery failed | Start redelivery/address investigation | `delivery_investigation`, `p2` |
| Marked delivered but user reports not received | Start investigation | `delivery_investigation`, `p1` |
| Package damaged | Offer return/exchange path and record delivery claim | `delivery_investigation`, `p1` when manual investigation is required |
| Wrong item or missing parts | Offer return/exchange path | `order_operation_review`, `p2` when automatic operation is unavailable |
| Missing/contradictory delivery facts | Do not invent status | `delivery_investigation`, `p1` |

Existing safety and staff-conduct policies can independently raise the primary
case priority. For example, a dangerous damaged product may be handled by the
existing risk policy rather than downgraded to an ordinary delivery case.

## 7. Support-case status inquiry

### 7.1 Visibility boundary

Until authentication and ownership verification are implemented, v0.5 may only
answer case-status questions for cases associated with the current LangGraph
`thread_id`. It must not accept an arbitrary case ID or order ID from a customer
and reveal a case belonging to another thread.

If several visible cases exist, the assistant lists a short summary and asks
which one the user means. It must not expose:

- internal actor identifiers;
- internal notes or event payloads;
- raw risk-classifier reasoning;
- idempotency keys;
- database version fields;
- other customers' or employees' personal data.

### 7.2 Customer-facing status mapping

| Internal status | Customer-facing status |
| --- | --- |
| `open` | Received |
| `in_progress` | In progress |
| `on_hold` + `waiting_customer` | Waiting for your information |
| other `on_hold` reason | Temporarily pending |
| `resolved` | Resolved |

A case status inquiry is read-only and never creates another support case merely
because the user asked for progress.

## 8. Proposed new case types and reason codes

Two explicit case types are recommended instead of overloading
`general_support`:

| Proposed type | Purpose |
| --- | --- |
| `order_operation_review` | Manual cancellation, return, or exchange decision |
| `delivery_investigation` | Carrier, tracking, or delivery investigation |

Recommended initial reason codes:

```text
cancellation_fulfillment_processing
cancellation_state_invalid
return_manual_amount_review
return_state_invalid
exchange_inventory_unknown
exchange_state_invalid
delivery_tracking_stalled
delivery_failed
delivery_marked_received_dispute
delivery_damage_claim
delivery_data_invalid
```

Business policy must depend on reason codes, never on display text. These reason
codes supplement rather than replace the v0.4 handoff reasons.

## 9. Proposed operation lifecycle

Order operations are not support cases and should have their own lifecycle:

```text
pending_confirmation -> submitted -> processing -> completed
                                  |-> manual_review
                                  |-> rejected
pending_confirmation -> cancelled_by_customer
manual_review -> processing | completed | rejected
```

The operation record should preserve `thread_id`, `source_message_id`,
`order_id`, `operation_type`, normalized reason, provider reference,
idempotency key, status, timestamps, and the order version used for evaluation.

## 10. Multi-intent rules

Recommended handling order:

1. apply existing hard/high/critical safety behavior;
2. resolve the existing low/medium risk-versus-order priority interrupt;
3. confirm an explicit human request when present;
4. identify one primary business operation;
5. load order facts and apply deterministic policy;
6. retain qualified complaint/handoff reasons;
7. finalize at most one primary support case under existing precedence rules.

If a message contains an inquiry plus one compatible operation, the operation is
primary and the response may also include relevant read-only facts. If it
contains two incompatible state-changing operations, the assistant asks the
user to choose before any policy execution.

## 11. Approved business decisions

The following decisions were approved on 2026-08-17 and form the phase-two
implementation contract:

1. Returns and exchanges use a **7-calendar-day** window measured from the
   delivery timestamp. The exact `delivered_at + 7 days` instant is included.
2. The manual-review threshold is currency-aware; the demonstration default is
   **`100 USD`**. An amount in an unsupported currency must not be compared to
   USD directly and should go to manual review until that currency is configured.
3. Cancellation during fulfillment `processing` requires **manual `p1`** review.
4. **72 hours** without a tracking event is `tracking_stalled`.
5. Add `order_operation_review` and `delivery_investigation` case types.
6. Every cancellation, return, and exchange request that will be submitted,
   including manual-review requests, requires one explicit confirmation.
7. Until v0.6 authentication and ownership verification, customers may query
   cases from the **current thread only**.
8. Order, payment, and fulfillment status are separate fields.
9. Lost, damaged, and wrong-item reports remain **unverified claims** until a
   Provider or human investigation confirms them.

## 12. Phase-two continuation point

After approval, phase two should implement only domain contracts and
deterministic policies:

- typed order snapshots and operation requests/results;
- cancellation, return, exchange, and delivery policy functions;
- Provider protocols with offline fakes;
- reason-code and status validation;
- exhaustive table-driven unit tests for the approved matrices.

Phase two should still avoid database migrations and LangGraph routing changes.

# v0.5 业务规则草案

状态：**已实现并完成 v0.5.0 发布验证**

目标版本：`v0.5.0`
本文档只定义业务规则和状态矩阵，不实现生产代码、数据库迁移或 LangGraph
工作流修改。

## 1. 目标与范围

v0.5 在现有退款、订单查询、投诉和人工交接能力之外，增加四项业务能力：

1. 取消订单；
2. 退货与换货；
3. 物流异常处理；
4. 面向客户的工单进度查询。

v0.4 已有的风险、投诉、退款与 handoff policy 继续生效。安全风险仍优先于
普通业务操作，最终是否允许业务操作必须由确定性规则决定，不能依赖 LLM
生成的自然语言。

### v0.5 不包含的内容

- 身份认证和权限控制；
- 验证订单是否属于当前用户；
- 接入真实 OMS、WMS、物流、库存、支付或 CRM 平台；
- 客服运营后台；
- SLA、通知和自动升级任务；
- 让 LLM 直接修改订单或判断业务资格。

因此 v0.5 仍是演示系统，内部 API 不能暴露给不可信用户，也不能处理真实
客户数据。

## 2. 通用决策原则

### 2.1 结构化事实与确定性决策

LLM 可以识别意图、提取原因、分类自由文本，但不能决定取消、退换货、物流
处理或数据可见性。领域 policy 只接收经过校验的结构化事实，并返回结构化
决策。

### 2.2 先读取再修改

所有订单操作遵循以下顺序：

```text
识别订单 -> 读取订单当前状态 -> 执行业务规则 -> 向用户解释结果
-> 必要时请求确认 -> 幂等提交操作
```

interrupt 恢复后必须再次读取订单并重新执行 policy，防止确认期间订单状态
已经发生变化。

### 2.3 确认边界

取消、退货和换货都会改变业务状态。所有将要提交的请求——包括自动处理和人工
审核——在提交前都必须进行一次明确确认。不符合条件、已经完成的幂等请求和状态
查询不需要操作确认。仅上报物流问题本身不需要确认，但创建
`delivery_investigation` 调查工单前需要一次明确确认。

一次确认只授权一个订单的一种操作，不能复用于后续轮次或其他订单。

### 2.4 幂等与并发

每次提交必须使用由 thread、来源消息、订单和操作类型形成的稳定幂等键。同一
请求重放时返回原结果，不能创建第二条操作。Provider 还需要识别过期的订单
version，并要求重新执行 policy。

### 2.5 每轮只执行一个主业务操作

一条触发消息可以包含多个事实和投诉原因，但最多提交一种主要订单操作。用户
同时要求取消和换货等互斥操作时，系统必须先询问用户选择，不能执行任意一种。

工单创建继续遵循 v0.4 规则：一条消息最多创建一个主工单，并保留全部原因。

### 2.6 继承现有风险与交接规则

- hard critical 继续绕过普通业务流程；
- semantic high/critical 继续使用现有风险响应；
- low/medium 风险和订单请求共存时继续让用户选择处理优先级；
- 已确认真人请求和正式投诉继续使用 v0.4 policy；
- 只有一般不满时不创建工单。

## 3. 订单快照所需契约

当前演示数据只覆盖 `shipped` 和 `delivered`，而且订单、物流、支付和退款事实
没有明确分层。v0.5 建议未来 Provider 至少返回：

| 字段 | 用途 |
| --- | --- |
| `order_id` | 稳定订单编号 |
| `version` | 乐观并发控制版本 |
| `order_status` | 商业订单生命周期 |
| `payment_status` | 独立的支付/退款生命周期 |
| `fulfillment_status` | 仓库和配送生命周期 |
| `amount`、`currency` | 金额规则与币种语义 |
| `created_at`、`shipped_at`、`delivered_at` | 时间规则 |
| `promised_delivery_at` | 确定性判断是否延迟 |
| `last_tracking_event_at` | 判断物流追踪是否停滞 |
| `return_eligible`、`exchange_eligible` | 由商品/订单系统提供的限制 |
| `active_operation` | 已存在的取消、退货或换货操作 |

建议把状态拆开：

```text
order_status:       pending_payment | confirmed | cancelled | completed
payment_status:     unpaid | paid | refund_pending | partially_refunded | refunded
fulfillment_status: unfulfilled | processing | shipped | delivered
```

这样不会把 `refunded` 同时误用为支付状态和物流状态。

## 4. 取消订单规则

| 当前事实 | 决策 | 确认 | 工单 |
| --- | --- | --- | --- |
| 待支付且未履约 | 自动取消 | 需要 | 无 |
| 已确认且未履约 | 允许取消，Provider 同步处理支付撤销 | 需要 | 无 |
| 仓库处理中 | 不自动取消，提交人工审核 | 需要 | `order_operation_review`，`p1` |
| 已发货 | 拒绝取消，提供物流帮助或签收后退货方案 | 不需要 | 默认无 |
| 已送达 | 拒绝取消，提供退换货评估 | 不需要 | 默认无 |
| 已取消 | 幂等返回已有成功结果 | 不需要 | 无 |
| 已在退款或已退款 | 不创建第二次资金操作 | 不需要 | 无 |
| 状态缺失、矛盾或过期 | 禁止自动修改，确认后转人工审核 | 需要 | `order_operation_review`，`p1` |

建议取消原因 code：

```text
ordered_by_mistake
no_longer_needed
incorrect_item_or_quantity
delivery_too_slow
payment_issue
other
```

原因用于审计和分析，v0.5 中不改变取消资格。

## 5. 退货与换货规则

### 5.1 共同条件

- 必须已经送达；
- `delivered_at` 合法，且距今不超过 7 个自然日；
- Provider 返回的对应商品资格为 true；
- 订单不能已经全额退款；
- 不能存在同类型未完成的重复操作。

退货和换货统一采用已确认的 7 个自然日窗口，从送达时间戳开始计算。
`delivered_at + 7 days` 的精确时刻仍可申请，只有超过该时刻才到期。商品是否允许
退换必须来自 Provider，LLM 不得自行推断。

### 5.2 退货

| 条件 | 决策 | 确认 | 工单 |
| --- | --- | --- | --- |
| 全部条件满足且金额 `< 100` | 提交退货 | 需要 | 无 |
| 全部条件满足且达到已配置人工审核阈值 | 人工审核 | 需要 | `order_operation_review`，`p1` |
| 尚未送达 | 拒绝并进入相应物流帮助 | 不需要 | 由物流规则决定 |
| 送达超过 7 个自然日 | 按标准规则拒绝 | 不需要 | 无，用户确认找人工时仍可按旧规则建单 |
| 商品不可退 | 根据结构化 Provider 原因拒绝 | 不需要 | 无 |
| 已有相同退货 | 幂等返回已有操作 | 不需要 | 无 |
| 数据缺失或矛盾 | 人工审核 | 需要 | `order_operation_review`，`p1` |

### 5.3 换货

| 条件 | 决策 | 确认 | 工单 |
| --- | --- | --- | --- |
| 共同条件满足且替换商品有库存 | 提交换货 | 需要 | 无 |
| 替换库存未知 | 人工审核 | 需要 | `order_operation_review`，`p2` |
| 替换商品无库存 | 拒绝换货并提供退货评估 | 不需要 | 无 |
| 已有相同换货 | 幂等返回已有操作 | 不需要 | 无 |
| 数据缺失或矛盾 | 人工审核 | 需要 | `order_operation_review`，`p1` |

建议标准化原因：

```text
changed_mind
wrong_item_received
damaged_item
defective_item
missing_parts
not_as_described
size_or_variant_issue
other
```

错发、破损、故障和缺件首先属于用户陈述，不能仅凭用户措辞就声称商家或物流
已经被证实存在责任。

### 5.4 与现有退款流程的关系

退货申请表示商品流转流程，提交申请时不能再独立执行一次退款。退货验收完成后
产生的退款，应由下游 Provider 只执行一次，或者通过稳定的 Provider 引用与已有
退款操作关联。

如果订单或订单行上已经存在退款、退货或换货操作，而新操作可能造成第二次资金
结果，policy 必须拒绝自动重复操作，并返回已有操作或转人工审核。v0.5 领域开发
期间不修改现有 v0.4 退款流程，但阶段二必须明确建模这条互斥规则。

## 6. 物流异常规则

支持的标准类型：

```text
delayed
tracking_stalled
delivery_failed
marked_delivered_not_received
package_damaged
wrong_item_or_missing_parts
other_delivery_issue
```

- 当前时间超过 `promised_delivery_at` 且订单未送达，才有确定性事实支持
  `delayed`；
- 已发货且至少 72 小时没有物流事件，才有确定性事实支持
  `tracking_stalled`；
- 其余类型在 Provider 或人工确认前均是用户 claim；
- 不能因为用户使用“丢件”一词就把物流责任描述为已证实事实。

| 问题 | 自助响应 | 工单 |
| --- | --- | --- |
| 承诺时间前认为延迟 | 解释实际状态，不断言存在事故 | 无 |
| 超过承诺时间的确定性延迟 | 展示追踪事实和下一步 | 用户要求调查或无有效追踪时建 `delivery_investigation`，`p2` |
| 物流至少 72 小时无更新 | 开始调查 | `delivery_investigation`，`p1` |
| 配送失败 | 调查重新配送或地址问题 | `delivery_investigation`，`p2` |
| 显示已送达但用户未收到 | 开始调查 | `delivery_investigation`，`p1` |
| 包裹破损 | 提供退换货路径并记录 claim | 需要人工调查时 `delivery_investigation`，`p1` |
| 错发或缺件 | 提供退换货路径 | 无法自动处理时 `order_operation_review`，`p2` |
| 物流数据缺失或矛盾 | 不虚构状态 | `delivery_investigation`，`p1` |

已有的安全和人员投诉 policy 可以独立提高主工单优先级，不能把危险商品等风险
降级成普通物流工单。

## 7. 工单进度查询

在 v0.6 实现认证和订单归属校验前，v0.5 只能查询与当前 LangGraph
`thread_id` 关联的工单。不能允许客户仅提供任意 case ID 或订单号就读取可能
属于其他人的工单。

客户可见状态映射：

| 内部状态 | 客户可见状态 |
| --- | --- |
| `open` | 已受理 |
| `in_progress` | 处理中 |
| `on_hold` + `waiting_customer` | 等待您补充信息 |
| 其他 `on_hold` | 暂时挂起 |
| `resolved` | 已解决 |

不能向客户返回内部操作人、内部备注、事件 payload、风险模型原始推理、幂等键、
数据库 version 或其他个人信息。仅查询进度不会创建新的工单。

## 8. 建议新增的工单类型和原因码

建议新增两种明确类型，不把所有业务都塞进 `general_support`：

| 类型 | 用途 |
| --- | --- |
| `order_operation_review` | 人工审核取消、退货或换货 |
| `delivery_investigation` | 物流、追踪和配送调查 |

建议首批 reason codes：

```text
cancellation_fulfillment_processing
cancellation_state_invalid
return_manual_amount_review
return_state_invalid
exchange_inventory_unknown
exchange_state_invalid
delivery_tracking_stalled
delivery_failed
delivery_marked_received_dispute
delivery_damage_claim
delivery_data_invalid
```

业务代码只能依赖 reason code，不能依赖展示文案。这些原因码是对 v0.4 handoff
原因的补充，不会替换旧原因。

## 9. 订单操作生命周期

订单操作与客服工单不是同一领域对象，建议使用独立状态：

```text
pending_confirmation -> submitted -> processing -> completed
                                  |-> manual_review
                                  |-> rejected
pending_confirmation -> cancelled_by_customer
manual_review -> processing | completed | rejected
```

操作记录建议保存 thread、来源消息、订单号、操作类型、标准化原因、Provider
引用、幂等键、状态、时间戳以及执行 policy 时使用的订单 version。

## 10. 多意图规则

建议处理顺序：

1. 执行已有 hard/high/critical 安全处理；
2. 处理已有 low/medium 风险与订单优先级选择；
3. 存在明确真人请求时进行确认；
4. 识别一种主业务操作；
5. 加载订单事实并执行确定性 policy；
6. 保留符合条件的投诉和 handoff 原因；
7. 根据现有优先级最多创建一个主工单。

查询和一种兼容操作同时出现时，以操作为主，同时可以返回有关的只读事实。两种
互斥修改操作同时出现时，必须先要求用户选择。

## 11. 已确认的业务决策

以下决策已于 2026-08-17 确认，并作为阶段二的实现契约：

1. 退货和换货统一采用 **7 个自然日**期限，从送达时间戳开始计算，
   `delivered_at + 7 days` 的精确时刻仍然有效。
2. 人工审核阈值按币种配置；演示环境默认 **`100 USD`**。对未配置币种，不能直接与
   USD 比较，应转人工审核。
3. 仓库 `processing` 状态的取消订单进入 **人工 `p1`** 审核。
4. 物流连续 **72 小时**无更新判定为 `tracking_stalled`。
5. 新增 `order_operation_review` 和 `delivery_investigation` 两种工单。
6. 所有将要提交的取消、退货和换货请求，包括人工审核请求，在提交前都必须进行
   一次明确确认。
7. v0.6 完成认证和归属校验前，客户只能查询**当前 thread**的工单。
8. 订单、支付和履约状态拆分为独立字段。
9. 丢失、破损和错发等在 Provider 或人工确认前均作为**未核实 claim**保存。

## 12. 阶段二接续点

审核通过后，阶段二只实现领域契约和确定性 policy：

- 类型化订单快照和操作请求/结果；
- 取消、退货、换货和物流 policy；
- Provider Protocol 与离线 fake；
- reason code 和状态转换校验；
- 覆盖全部已批准矩阵的参数化单元测试。

阶段二仍不修改数据库，也不接入 LangGraph 路由。
