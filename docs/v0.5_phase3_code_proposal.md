# v0.5 Phase Three Code Proposal

Status: **Implemented; Docker migration and API startup validated locally**

Phase three persists the v0.5 cancellation, return, and exchange domain. It
does not modify LangGraph, nodes, routing, prompts, the refund flow, or the
current internal support-case API.

## Proposed files

- `src/agent/sql/migrations/0004_order_operations.sql`
- `src/agent/operations/models.py` (persisted models and service result models)
- `src/agent/operations/repository.py` (Protocol and domain errors)
- `src/agent/operations/postgres_repository.py` (async PostgreSQL adapter)
- `src/agent/operations/service.py` (idempotent application service)
- `tests/unit_tests/test_operation_service.py`
- `tests/integration_tests/test_postgres_order_operation_repository.py`

No Compose change is required. The existing migration service already discovers
all numbered SQL files before the API starts.

## Migration design

Only a new `0004` migration is added. Migrations `0002` and `0003` remain
unchanged because their checksums may already be stored in
`case_management.schema_migrations`.

The migration expands the existing support-case type check with the approved
values `order_operation_review` and `delivery_investigation`. It also expands
the two existing reason-code checks with approved operation and delivery reason
codes. Existing data satisfies the broader checks and is not deleted or changed.

Replacing a PostgreSQL table constraint takes a short `ACCESS EXCLUSIVE` lock.
That is safe during a controlled local Compose restart. A production deployment
would schedule this migration window.

The new `case_management.order_operations` aggregate stores:

- identity: operation ID, idempotency key, thread ID, source message ID;
- request: order ID, operation type, user reason code, optional exchange variant,
  message excerpt;
- evaluated facts: order version, amount, currency, manual-review case type and
  priority, policy reason codes, and display reason snapshot;
- execution: status, provider reference, optional linked support case;
- audit/concurrency: creation/update timestamps and optimistic version.

Its statuses are `pending_confirmation`, `submitted`, `processing`,
`manual_review`, `completed`, `rejected`, and `cancelled_by_customer`.

The database enforces a unique idempotency key, one operation per
`(thread_id, source_message_id)`, required replacement variant for exchanges,
manual-review metadata consistency, and a foreign key to a linked support case.
A partial unique index allows only one active whole-order operation while it is
pending, submitted, processing, or under manual review.

The new `case_management.order_operation_events` table records immutable
`operation_created`, `confirmation_recorded`, `status_changed`, and
`support_case_attached` events. Every event has its own unique idempotency key.

### Two different reason-code fields

The operation aggregate stores `request_reason_code` and `policy_reason_codes`
separately.

- `request_reason_code` records normalized user intent, such as `changed_mind`,
  `damaged_item`, or `no_longer_needed`.
- `policy_reason_codes` records the deterministic reason for the decision, such
  as `return_manual_amount_review`, `exchange_inventory_unknown`, or
  `delivery_tracking_stalled`.

Only policy reason codes can later be copied to a support case. Display text is
an audit snapshot only and never participates in a business decision.

## Repository and service

`OperationRepository` follows the existing `CaseRepository` pattern: get by ID,
find by source message, find event by idempotency key, find active order,
atomically create aggregate plus event, and atomically update aggregate plus
event with an expected version.

`PostgresOrderOperationRepository` translates named constraints into explicit
errors for duplicate source messages, duplicate idempotency keys, active-order
conflicts, stale versions, missing records, and unexpected persistence failures.
Create/update and their immutable event are committed together in one database
transaction.

`OperationService` has five operations:

- `create_pending_operation`: eligible/manual decision creates a
  `pending_confirmation` record; duplicate source returns the original record.
- `confirm_operation`: automatic operations become `submitted`; manual requests
  become `manual_review`; confirmation and status events are both persisted.
- `cancel_pending_operation`: only permits
  `pending_confirmation -> cancelled_by_customer`.
- `update_operation_status`: validates internal/provider transitions with an
  optimistic lock.
- `attach_support_case`: only allows one case link on a manual-review operation.

Every confirmation/update receives a stable request ID. The service derives an
event idempotency key from it, so network retries cannot append events or advance
the state twice.

After confirmation, a manual request goes directly to `manual_review`; it does
not falsely claim that an automated Provider accepted it.

## Future graph relation

This phase only makes the two new support-case types persistable. Stage four
will use `CaseService` to create/reuse an `order_operation_review` case after a
manual operation is confirmed, then call `attach_support_case`. Delivery issues
will create `delivery_investigation` cases directly and do not create operation
records because they are not mutations.

## Tests

Offline unit tests cover create/confirmation idempotency, permitted and rejected
status transitions, pending cancellation, manual-review requirements, and case
attachment rules.

Optional PostgreSQL integration tests reuse `CASE_TEST_POSTGRES_URI` and cover
migration application, row/event round trips, confirmation idempotency,
active-order conflicts, and cleanup. They remain skipped until a disposable
test database URI is configured.

# v0.5 阶段三代码方案

状态：**已实现，并已在本地验证 Docker 迁移和 API 启动**。

阶段三将取消、退货、换货领域持久化到 PostgreSQL；不修改 Graph、nodes、routing、
prompts、退款流程或现有内部工单 API。

新增 `0004_order_operations.sql`、订单操作 Repository、PostgreSQL Repository、
OperationService、单元测试和可选 PostgreSQL 集成测试。现有 Compose 不需要修改。

迁移只新增，不修改已执行的 `0002`、`0003`。它会扩展工单类型和 reason-code
约束，支持 `order_operation_review`、`delivery_investigation`，并新增：

- `order_operations`：订单操作状态、订单快照、人工审核建议、Provider 引用、关联工单和乐观锁；
- `order_operation_events`：创建、确认、状态变更、关联工单的不可变审计历史。

数据库会保证：操作幂等、同一来源消息只能创建一个主操作、换货必须有 variant、
人工审核字段完整、关联工单外键有效，以及一个订单同时只能有一条未解决操作。

Service 状态机如下：

- 创建请求：`pending_confirmation`；
- 确认自动操作：进入 `submitted`；
- 确认人工审核：直接进入 `manual_review`；
- 用户取消确认：进入 `cancelled_by_customer`；
- 内部/Provider 更新：校验状态转换并使用乐观锁；
- 关联工单：仅人工审核操作允许，且记录不可变事件。

每次确认或更新必须使用稳定 request ID，重试不会重复写事件或推进状态。替换
PostgreSQL 现有检查约束会有短暂表锁；本地 Compose 可以在受控重启时执行，生产需
安排迁移窗口。

阶段四才会把已确认的人工审核操作接入 Graph，创建或关联真正的人工工单。

订单操作会分别保存“用户请求原因”和“policy 原因码”。例如 `damaged_item` 是用户
陈述；`return_manual_amount_review`、`exchange_inventory_unknown` 才是系统决定
人工审核的业务依据。后续工单只使用 policy 原因码，展示文案不参与业务判断。
