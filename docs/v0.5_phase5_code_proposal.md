# v0.5 Phase Five Code Proposal

Status: **Implemented and validated for the v0.5.0 release**

Phase five closes the v0.5 release scope through regression coverage,
repeatable validation guidance, and documentation. It does not introduce a new
customer-service capability, database migration, workflow redesign, or an
external OMS/WMS/carrier integration.

## 1. Goal

The earlier phases establish the domain policy, persistence boundary, and
LangGraph subflow. This final phase verifies that the complete customer-facing
behavior is safe to demonstrate and that a future contributor can reproduce
the tests without inferring hidden setup steps.

The release target remains a local demonstration system. `DemoOrderProvider`
is not a production order-management integration.

## 2. Automated regression coverage

The implementation will extend the existing tests rather than create a second
test framework.

### 2.1 Operation-subflow cases

Add deterministic Graph integration tests for the cases not yet covered by the
current end-to-end Graph tests. These tests have now been added to the existing
`tests/integration_tests/test_graph.py` module:

| Scenario | Expected result |
| --- | --- |
| Eligible return below USD 100 | One confirmation, then `submitted`; no support case |
| Return at USD 100 | One confirmation, then `manual_review` and P1 `order_operation_review` case |
| Eligible exchange with an available variant | One confirmation, then `submitted` |
| Exchange with an unavailable variant | Deterministic rejection; no persisted operation or case |
| Ambiguous request such as cancellation plus exchange | Clarifying response; no persisted operation or case |
| User declines a pending operation | Operation becomes `cancelled`; no Provider submission or support case |
| User confirms stalled tracking | One confirmation, then P1 `delivery_investigation` case; no order-operation row |
| User declines stalled-tracking investigation | No delivery case is created |

The tests will keep using the in-memory repository, `DemoOrderProvider`, and a
deterministic structured-output fake. They will not call an LLM or Docker.

### 2.2 Persistence and idempotency checks

Add or extend service/repository tests to verify. The existing service suite
already covered automatic Provider idempotency and support-case attachment; it
now also covers the fact that a customer-declined pending operation cannot later
be submitted:

- an automatic operation is submitted to the Provider once even when its
  confirmation path is replayed;
- a declined operation cannot later be submitted through the same persisted
  record;
- manual-review operation events retain their support-case attachment;
- one thread can hold distinct unresolved `order_operation_review` and
  `delivery_investigation` cases when separate triggering messages justify
  each one.

No applied migration will be changed. The optional PostgreSQL tests remain
guarded by `CASE_TEST_POSTGRES_URI` and must use a disposable database.

## 3. API and Docker acceptance runbook

README now contains a v0.5 acceptance-test section with the exact API-document
workflow:

1. start `docker compose up --build -d` and verify `/ok`;
2. create an `agent` assistant and a thread;
3. run the automatic cancellation scenario with `ORD-10008`, resume `true`,
   and confirm `operation_status: submitted`;
4. run manual cancellation with `ORD-10009`, resume `true`, and confirm P1
   `order_operation_review`;
5. run stalled tracking with `ORD-10010`, verify the confirmation interrupt,
   then resume `true` and confirm P1 `delivery_investigation`;
6. send `What is my support request status?` in the same thread and verify that
   only that thread's cases are listed.

The runbook will explicitly state that the API calls create local demonstration
records in PostgreSQL. It will also distinguish an initial container-startup
race from a real API failure: wait for `docker compose ps` to report the API
healthy before calling `/ok`.

## 4. Documentation updates

README now describes:

- the v0.5 operation lifecycle: read current snapshot -> deterministic policy
  -> explicit confirmation -> idempotent Provider submission or case handoff;
- the boundary between `orders.json` (the existing v0.4 lookup demo) and
  `DemoOrderProvider` (the richer v0.5 operation demo);
- all v0.5 demonstration order scenarios, including `ORD-10008` through
  `ORD-10011`;
- the fact that `submitted` means accepted by the demo Provider, not completed
  by a real warehouse, payment system, or carrier.

The English README section will remain before the corresponding Chinese
section.

## 5. Explicit non-goals

Phase five will not:

- change refund, risk, complaint, or v0.4 handoff decisions;
- add authentication, customer ownership checks, or public access control;
- add external integrations or production credentials;
- alter `0001` through `0004` migrations;
- run `git add`, `git commit`, `git tag`, or `git push`.

## 6. Completion criteria

Phase five is ready for release review when:

- the full offline test suite, Ruff, mypy, and package build pass;
- the optional PostgreSQL tests are documented and remain safely isolated;
- the local Docker/API acceptance flow has been performed successfully;
- README accurately documents the actual v0.5 behavior and its demo-only
  limitations;
- no unrelated files or secrets are staged for release.
