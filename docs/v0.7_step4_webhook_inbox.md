# v0.7 Step 4 — Provider webhooks and Inbox processing

Status: implemented and verified through the Provider messaging subsystem
test matrix. This step completes the asynchronous callback half of the v0.7
Provider flow without adding Provider calls to LangGraph.

## Flow

```text
Provider callback
  -> POST /webhooks/providers/{provider_connection_id}
  -> bounded raw-body read + trusted connection lookup + HMAC verification
  -> durable Inbox receive (idempotent on connection + event ID)
  -> standalone Inbox worker claim + lease renewal
  -> locked Inbox / Attempt / canonical Outbox revalidation
  -> order-operation status event or support-case provider_update
  -> Inbox + Attempt finalization in the same transaction
```

The HTTP request only authenticates, validates, and stores the callback. It
never updates an order operation or support case directly. Domain changes are
owned by `PostgresInboxFinalizer` after the standalone Inbox worker claims the
persisted message.

## Webhook trust boundary

The route accepts `application/json` only, rejects content encoding other than
`identity`, and limits the actual streamed request body to 256 KiB. Exactly one
non-empty value is required for each protected header:

- `X-Provider-Event-Id`
- `X-Provider-Timestamp`
- `X-Provider-Signature`

The signature is lowercase hexadecimal HMAC-SHA256 over the Step 1 canonical
payload `{timestamp}.{event_id}.{raw_body_bytes}`. The route resolves the
trusted tenant, signing secret, and validity window from
`PROVIDER_WEBHOOK_CONNECTIONS_JSON` by the path connection ID. Request-body
tenant or connection values never establish trust.

Successful durable receipt returns `202 {"status":"accepted"}`. Authentication
failures return 401, verified payload failures 400, event-ID conflicts 409,
and persistence unavailability 503. Responses do not contain secrets, raw
bodies, signatures, Provider references, business identifiers, SQL, or
constraint details.

Only the validated typed event and `SHA-256(raw_body)` are persisted. Raw
bodies and signatures are not stored. An exact callback replay returns the
existing Inbox row; the same connection/event ID with any trusted-field change
is rejected without overwriting it.

## Finalization rules

Before any domain write, the finalizer locks the persisted Inbox and verifies
its live lease, worker, and Attempt fencing identity. It rebuilds the canonical
Outbox envelope and checks command, tenant, connection, aggregate, payload,
customer, order, source-message, and local aggregate associations.

- Order-operation callbacks apply the deterministic status policy. Applied
  changes update the operation and append one `status_changed` event. Duplicate
  and stale callbacks complete the Inbox without moving the aggregate.
- Delivery-investigation callbacks never mutate or auto-resolve the support
  case. They append one immutable `provider_update` event.
- Inbox and Attempt completion, domain changes, and domain events commit in one
  PostgreSQL transaction. Constraint failures roll the entire transaction
  back.
- A callback waits for an unfinished Outbox with bounded retry scheduling. The
  fifth processing failure is terminal. Expired, forged, recovered, or stale
  leases cannot finalize another worker's claim.

Distinct callbacks for the same support case may both append their independent
audit events. Two finalizers using the same claimed handle produce one applied
result and one fenced loser.

## Configuration and processes

Inbound trust configuration is separate from outbound Provider credentials:

```dotenv
PROVIDER_WEBHOOK_CONNECTIONS_JSON=[{"connection_id":"provider-demo","tenant_id":"tenant-demo","signing_secret":"replace-me","validity_window_seconds":300}]
INBOX_WORKER_ID=
```

The placeholder is illustrative only. Use a secret manager or protected
runtime configuration outside local development and never reuse the outbound
Provider credential as the webhook signing secret.

For local processes, apply migrations and start the API, Outbox worker, and
Inbox worker separately:

```powershell
uv run python scripts/apply_migrations.py
uv run python -m agent.integrations.worker_main
uv run python -m agent.integrations.inbox_worker_main
```

Both workers load `.env` without overriding variables already present in the
process environment. Missing or empty worker IDs use a hostname-derived
fallback. Each worker owns and closes its PostgreSQL pool; the Outbox worker
also owns its HTTP client. Cancellation and startup failures are propagated.

Docker Compose runs `outbox-worker` and `inbox-worker` as separate services
after migrations complete and PostgreSQL is healthy. Neither exposes a port or
depends on the API or Redis. The Outbox worker receives only its database and
outbound Provider configuration; the Inbox worker receives only its database
URI and worker ID. Webhook signing secrets remain in the API process.

## Verification boundary

The PostgreSQL integration suite covers accepted, processing, completed,
rejected, duplicate, stale, association mismatch, missing records, retry
exhaustion, fencing, event-conflict rollback, and concurrent finalizers for
both supported aggregates. A full cross-component test sends two signed HTTP
callbacks, persists them, processes both in one Worker batch, and proves that
HTTP replay plus a second Worker run creates no duplicate Inbox, Attempt, or
domain event.

## Deliberate v0.7 limits

- Environment-backed connection resolvers are startup snapshots; secret
  rotation requires a process restart.
- PostgreSQL is the queue and lease coordinator. There is no broker, dead-letter
  UI, or distributed rate limiter.
- Rate limiting is process-local for the Outbox worker.
- Failed Inbox messages have no public manual-redrive API.
- The retention periods recorded in Step 2 have no cleanup job yet.
- Support-case Provider updates are audit-only and do not auto-resolve a case.
- Worker liveness is managed by the process supervisor or Compose restart
  policy; v0.7 does not expose a business-health endpoint for worker loops.

These limits are intentional operational debt, not hidden success criteria for
Step 4. Version closure must still run the v0.7-wide validation and version
consistency checks.
