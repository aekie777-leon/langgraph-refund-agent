# v0.7 Step 2 — Provider Messaging Persistence (Outbox / Inbox / Leases)

> Status: implemented in migration `0007_provider_messaging.sql` and
> `agent/integrations/*`. Worker, HTTP adapter, simulator, and webhook route
> are **not** part of this step.

## 1. What this step builds

- Transactional Outbox (`integration.outbox_messages`)
- Webhook Inbox (`integration.inbox_messages`)
- Delivery-attempt audit (`integration.outbox_delivery_attempts`)
- Inbox-processing-attempt audit (`integration.inbox_processing_attempts`)
- Manual redrive audit (`integration.outbox_redrives`)
- `FOR UPDATE SKIP LOCKED` multi-worker claiming, leases, fencing tokens
- Worker-crash lease recovery
- Atomic domain + event + outbox writes for order operations and
  delivery-investigation cases
- Per-order delivery-investigation case isolation

## 2. Tables (migration 0007)

| Table | Purpose | Unique constraints |
| --- | --- | --- |
| `integration.outbox_messages` | one provider command | `command_id`; `(tenant_id, idempotency_key)` |
| `integration.outbox_delivery_attempts` | one delivery attempt | `(command_id, delivery_cycle, attempt_number)` |
| `integration.outbox_redrives` | one manual redrive (immutable) | `(tenant_id, request_id)` |
| `integration.inbox_messages` | one verified webhook event | `(provider_connection_id, event_id)` |
| `integration.inbox_processing_attempts` | one inbox processing attempt | `(inbox_id, attempt_number)` |

All timestamps are `TIMESTAMPTZ`; all tenant/connection/worker/error texts
reject blank values via `CHECK`; UUIDs are application-generated; no secrets
are ever stored. `payload` is `JSONB` holding only the strong-typed payload
(the outbox stores the command payload; the inbox stores the validated
`ProviderWebhookEventData`), and `raw_body_sha256` stores `SHA-256(raw_body)`
as 64-char lowercase hex — never the raw body or signature. Every error
field (`last_error_code`, `last_error_message`, `safe_error_code`,
`safe_error_message`) is `VARCHAR(500)` with a non-blank `CHECK`, matching the
Pydantic models, and may never carry raw provider responses, bodies,
signatures, or secrets.

Outbox CHECK invariants: status ∈ `pending | processing | retry_scheduled |
published | dead`; `processing` requires the full lease
(`lease_id`+`lease_owner`+`lease_expires_at`) and non-processing rows must not
carry a lease; `published` ⟺ `published_at`; `dead` ⟺ `dead_at`;
`delivery_cycle >= 1`; `attempts_in_cycle BETWEEN 0 AND 8` (a cycle may never
consume a 9th attempt); JSON payload must be an object; `order_operation`
requires `expected_order_version` while `support_case` forbids it;
command/aggregate pairs and capability/command values use the step-1
vocabulary.

Inbox CHECK invariants: status ∈ `received | processing | processed |
failed`; same lease rules; `processed` ⟺ `processed_at`; `failed` ⟺
`failed_at`; `raw_body_sha256 ~ '^[0-9a-f]{64}$'`.

Attempt tables: `outcome` and `finished_at` appear together; failure kinds use
the step-1 vocabulary; `retry_after_seconds` rejects NaN/±Infinity at the
database too.

## 3. Outbox / Inbox state machines

Outbox:

```
pending / retry_scheduled --claim--> processing --accepted--> published
                                    |--retry (attempts < 8)--> retry_scheduled
                                    |--terminal failure---------> dead
                                    |--lease expiry (1st..7th attempt)--> retry_scheduled
                                    |--lease expiry (8th attempt)------> dead
dead --manual redrive--> retry_scheduled (delivery_cycle + 1)
```

The 8-attempt cap is enforced twice: the database rejects
`attempts_in_cycle > 8`, the claim only picks rows with
`attempts_in_cycle < 8`, and `schedule_outbox_retry` refuses to schedule a
retry when the cycle already consumed 8 attempts
(`OutboxAttemptsExhaustedError`, transaction fully rolled back). A redrive
opens a new cycle with `attempts_in_cycle = 0`, so the new cycle may again
consume up to 8 attempts, while the original `idempotency_key` is preserved.

Inbox:

```
received --claim--> processing --processed--> processed
                               |--retryable (attempts < 5)--> received (later due)
                               |--terminal failure-----------> failed
                               |--lease expiry (recovery)----> received
```

`processed` and `failed` are terminal; `failed` is never re-claimed by the
regular claim (`claim_due_inbox` only picks `received`). Automatic attempt
caps: outbox 8 per delivery cycle, inbox 5. Inbox max attempts is applied by
the future worker via `schedule_inbox_retry`; this step provides the cursor
helper and the lease/attempt machinery.

## 4. Claiming, leases, and fencing

- Claiming uses `FOR UPDATE SKIP LOCKED`, ordered by
  `available_at, created_at, command_id` (outbox) and
  `available_at, received_at, inbox_id` (inbox), limited by the batch size.
- The claim transaction locks candidate rows, sets `status = 'processing'`,
  increments `attempts_in_cycle` / `processing_attempts`, writes
  `lease_id` / `lease_owner` / `lease_expires_at` (defaults: outbox 90 s,
  inbox 60 s, batch 20 — all configurable at call sites, not hard-coded
  business constants), and inserts the attempt row.
- Completion / failure / renewal must match `command_id`/`inbox_id` +
  `lease_id` + `lease_owner` + `status = 'processing'`; a stale worker's
  update after its lease was recovered matches nothing and raises
  `LeaseConflictError` (fencing).
- Attempt finalization uses the full fencing identity: delivery attempts
  match `attempt_id` + `command_id` + `lease_id` + `worker_id` +
  `finished_at IS NULL`; inbox attempts match `attempt_id` + `inbox_id` +
  `lease_id` + `worker_id` + `finished_at IS NULL`. A mismatched caller can
  never finish another command's or worker's attempt, and every affected row
  count must be exactly 1 inside one transaction or the whole transaction
  rolls back.
- All time comparisons prefer PostgreSQL `clock_timestamp()` so worker-host
  clock skew cannot extend leases or delay recovery. Renewing requires the
  current lease to still be valid (`lease_expires_at > clock_timestamp()`);
  an expired lease is never resurrected.

## 5. Lease recovery (crash recovery)

`recover_expired_outbox_leases` / `recover_expired_inbox_leases` find
`processing` rows whose `lease_expires_at` is in the past, `FOR UPDATE SKIP
LOCKED` them, mark the unfinished attempt `lease_expired`, and clear the
lease. For the outbox: if the expired attempt is the 1st..7th of the cycle,
the message returns to `retry_scheduled` with `available_at =
clock_timestamp()`; if it is already the 8th, the message goes straight to
`dead` with `dead_at` set (safe error code
`lease_expired_attempts_exhausted`), never back to `retry_scheduled`. No
inaccurate `last_failure_kind` is invented for a worker crash. The delivery
cycle is preserved and consumed attempt numbers are never rewound.

## 6. Atomic domain + outbox writes

First writes never go through a standalone `enqueue()`:

- `OperationRepository.queue_operation_with_events_and_command(scope,
  operation, events, command, expected_version)` — operation update + domain
  events + outbox row in one transaction.
- `CaseRepository.create_case_with_event_and_command(scope, case, event,
  command)` and `update_case_with_event_and_command(scope, case, event,
  command, expected_version)` — case write + event + outbox row in one
  transaction.

Any failure (optimistic-lock conflict, unique violation, CHECK violation)
rolls back all three. Before any connection or transaction is acquired, every
atomic method verifies that the domain object, its events, and the command
describe the same aggregate — on typed identifiers only, never on display
text. The command envelope is first re-validated from its serialized form
(`model_dump` → `model_validate`) so a `model_copy`-tampered instance cannot
bypass the envelope validators; a failed re-validation raises
`ValueError("command envelope is invalid")` with the original
`ValidationError` preserved as the cause:

- order operations: `operation.status == 'queued'`,
  `operation.version == expected_version + 1`,
  `command.aggregate_type == 'order_operation'`,
  `command.aggregate_id == operation.operation_id`,
  `command.tenant_id / customer_id / source_message_id` match the operation,
  `command.expected_order_version == operation.order_version`,
  `command.payload.order_id == operation.order_id`,
  `command.payload.operation_type == operation.operation_type`, and every
  event's `operation_id` / `tenant_id` / `customer_id` matches.
- delivery-investigation cases: `case.case_type == 'delivery_investigation'`
  with a non-null `order_id`, `command.command_type ==
  'delivery_investigation'`, `command.aggregate_type == 'support_case'`,
  `command.aggregate_id == case.case_id`, `tenant_id` / `customer_id` /
  `source_message_id` match, `expected_order_version is None`,
  `command.payload.order_id == case.order_id`, and the event's `case_id` /
  `tenant_id` / `customer_id` matches.

The command is inserted by
`insert_outbox_message` (cursor-scoped helper) from the validated
`ProviderCommandEnvelope`; the capability is derived as `order_operation`
for every v0.7 command. `payload` stores only the strong-typed command
payload; all searchable envelope metadata lives in dedicated columns. Reading
an outbox row rebuilds the `ProviderCommandEnvelope` with `to_envelope()` and
re-validates it through Pydantic.

The existing command-free repository methods remain untouched so the graph
and existing tests are unaffected.

## Inbox event_id: exact replay vs collision

`receive_inbox_idempotently` keeps the unique constraint
`(provider_connection_id, event_id)` and inserts with
`ON CONFLICT DO NOTHING`, so concurrency is safe. When the insert hits the
existing row, the stored record is compared deterministically against the
incoming request on every trusted field: `provider_connection_id`,
`event_id`, `tenant_id`, `schema_version`, `event_type`, `command_id`,
`aggregate_type`, `aggregate_id`, `raw_body_sha256`, and the canonical typed
payload.

- All equal → the request is an **exact replay**: the existing
  `InboxMessage` is returned and no second row is created.
- Any difference → `InboxEventConflictError` is raised; the original row is
  never overwritten. The error message names only the conflicting fields and
  never contains raw bodies, signatures, secrets, or the full payload.

## 7. Delivery-investigation uniqueness

The single active-case unique index is replaced by two partial indexes:

- non-delivery: `(tenant_id, thread_id, case_type)` where
  `status IN ('open','in_progress','on_hold')` and
  `case_type <> 'delivery_investigation'`
- delivery: `(tenant_id, thread_id, case_type, order_id)` where
  `status IN ('open','in_progress','on_hold')` and
  `case_type = 'delivery_investigation'`

`delivery_investigation` rows must carry a non-blank `order_id` (DB CHECK +
model validator). `find_unresolved_case` gained an `order_id` parameter and
the case service passes `trigger.order_id` for delivery investigations, so the
same thread with different orders creates distinct investigation cases while
all other case types keep their previous thread+type reuse.

The active order-operation uniqueness is tenant-scoped: the partial unique
index is `(tenant_id, order_id)` for
`status IN ('pending_confirmation','queued','submitted','processing','manual_review')`,
so different tenants may use the same `order_id` while one tenant may only
have one active operation per order; `customer_id` is deliberately not part of
the key. Terminal operations (completed / rejected / cancelled) never block a
new active operation.

## 8. Redrive preserves provider idempotency

`redrive_dead_outbox` only accepts `dead` messages, then in one transaction:
`delivery_cycle + 1`, `attempts_in_cycle = 0`, `available_at =
clock_timestamp()`, clears `dead_at` and any lease — and **keeps the original
`idempotency_key`** so the provider still deduplicates on the same stable key.
An immutable `outbox_redrives` row records the request; the
`(tenant_id, request_id)` uniqueness rejects duplicate requests
(`DuplicateRedriveRequestError`). No HTTP API is implemented in this step.

## 9. Deliberately not public

- No `mark_outbox_published`, `mark_inbox_processed`, or similar standalone
  repository methods for operations that also update domain aggregates: the
  future transaction coordinator must compose them with the aggregate update
  in one transaction using the cursor-scoped helpers in
  `agent/integrations/postgres_writes.py` (`insert_outbox_message`,
  `update_outbox_transition`, `finish_delivery_attempt`,
  `mark_inbox_processed`, `finish_inbox_attempt`, `mark_inbox_failed`,
  `schedule_inbox_retry`).
- The write helpers never acquire connections or open transactions and are
  not exposed through `agent.integrations` or the graph.
- No worker loop, HTTP adapter, simulator, webhook route, redrive API, or
  retention cleanup job.

## 10. Data retention policy (recorded, not implemented)

| Data | Retention |
| --- | --- |
| processed inbox messages + inbox processing attempts | 90 days |
| published outbox messages + delivery attempts + redrives | 180 days |
| dead outbox / failed inbox | retention starts only after the issue is resolved |

## 11. Domain adjustments

- `OperationRecordStatus` gained `queued` with transitions
  `pending_confirmation → queued`, `queued → submitted | manual_review |
  rejected` (compat transition `pending_confirmation → submitted` retained).
  `queued` joined the active status set, the partial unique index
  `uq_order_operations_active_order`, repository queries, test fakes, and
  service transition maps. The graph does not use `queued` yet.
- `CaseEventType` gained `provider_update`; `SupportCaseEvent` gained
  `provider_command_id`, `provider_command_status`
  (`ProviderCommandExecutionStatus`), and `provider_reference`. A
  `provider_update` event requires the command id, the status, and an actor
  (e.g. `system`), must not carry `previous_status`/`current_status`, never

- `HandoffReason` gained `provider_delivery_failed` (Python literal and both
  reason-code CHECK constraints).

## 12. How step 3 consumes this

A future worker: `claim_due_outbox` → rebuild envelope via
`to_envelope()` → deliver through the adapter → compose, in one transaction,
the domain update, the domain event, `finish_delivery_attempt`, and
`update_outbox_transition` (published / dead / retry_scheduled) via the
cursor helpers. Inbox side: `receive_inbox_idempotently` (route),
`claim_due_inbox`, re-verify `command_id` / `provider_connection_id` /
`tenant_id` / `aggregate_type` / `aggregate_id` against the local outbox
command, then compose the aggregate update + `mark_inbox_processed` +
`finish_inbox_attempt` atomically; `provider_update` events append to
`support_case` only. `recover_expired_*` runs on startup; leases renew via
`renew_outbox_lease` / `renew_inbox_lease`.

## 3. Outbox / Inbox 状态机

Outbox：

```
pending / retry_scheduled --claim--> processing --accepted--> published
                                    |--retry（attempts < 8）--> retry_scheduled
                                    |--terminal failure----------> dead
                                    |--lease 过期（第 1～7 次）----> retry_scheduled
                                    |--lease 过期（第 8 次）------> dead
dead --人工 redrive--> retry_scheduled（delivery_cycle + 1）
```

8 次上限由两层共同保证：数据库 CHECK 拒绝 `attempts_in_cycle > 8`，
claim 只领取 `attempts_in_cycle < 8` 的行，`schedule_outbox_retry` 在第 8
次之后拒绝再调度重试（`OutboxAttemptsExhaustedError`，事务整体回滚）。
redrive 开启新 cycle 时 `attempts_in_cycle = 0`，新 cycle 最多可再次消耗
8 次 Attempt，原始 `idempotency_key` 保持不变。

Inbox：

```
received --claim--> processing --processed--> processed
                               |--retryable（attempts < 5）--> received（延期到期）
                               |--terminal failure-----------> failed
                               |--lease 过期（恢复）-----------> received
```

`processed` 与 `failed` 都是终态；普通 claim 只领取 `received`，`failed`
不会被自动重新领取。自动尝试上限：Outbox 每个 delivery cycle 8 次，Inbox
5 次。Inbox 的尝试上限由未来 Worker 通过 `schedule_inbox_retry` 应用；
本步骤提供 cursor helper 与 lease/attempt 机制。

## 4. 领取、Lease 与 fencing

- 领取使用 `FOR UPDATE SKIP LOCKED`，按 `available_at, created_at,
  command_id`（Outbox）/ `available_at, received_at, inbox_id`（Inbox）
  排序并按 batch 限制。
- 领取事务锁定候选行、置 `status = 'processing'`、递增
  `attempts_in_cycle` / `processing_attempts`、写入 `lease_id` /
  `lease_owner` / `lease_expires_at`（默认：Outbox 90 秒、Inbox 60 秒、
  batch 20 —— 全部在调用点可配置，不是写死的业务常量），并插入 Attempt 行。
- 完成 / 失败 / 续租必须同时匹配 `command_id`/`inbox_id` + `lease_id` +
  `lease_owner` + `status = 'processing'`；旧 Worker 在 lease 被恢复后
  的任何更新都匹配不到行，抛出 `LeaseConflictError`（fencing）。
- Attempt 收尾使用完整 fencing 身份：投递 Attempt 匹配 `attempt_id` +
  `command_id` + `lease_id` + `worker_id` + `finished_at IS NULL`；Inbox
  Attempt 匹配 `attempt_id` + `inbox_id` + `lease_id` + `worker_id` +
  `finished_at IS NULL`。不匹配的调用者永远无法结束其他命令或 Worker 的
  Attempt；任何 affected 行数不为 1 都会使整个事务回滚。
- 时间比较优先使用 PostgreSQL `clock_timestamp()`，避免 Worker 主机时钟
  偏差延长 lease 或延迟恢复。续租要求当前 lease 仍然有效
  （`lease_expires_at > clock_timestamp()`），已过期的 lease 不会被复活。

## 5. Lease 恢复（崩溃恢复）

`recover_expired_outbox_leases` / `recover_expired_inbox_leases` 查找
`processing` 且 `lease_expires_at` 已过期的行，`FOR UPDATE SKIP LOCKED`
锁定，将未结束的 Attempt 标记为 `lease_expired` 并清除 lease。Outbox 侧：
如果过期 Attempt 是本 cycle 的第 1～7 次，消息回到 `retry_scheduled`，
`available_at = clock_timestamp()`；如果已是第 8 次，消息直接进入 `dead`
并设置 `dead_at`（安全 error code `lease_expired_attempts_exhausted`），
绝不回到 `retry_scheduled`。不为 Worker 崩溃编造不准确的
`last_failure_kind`。delivery cycle 保持不变，已消耗的 attempt_number 不回退。

## 6. 领域 + Outbox 单事务

首次写入不经过独立的公开 `enqueue()`：

- `OperationRepository.queue_operation_with_events_and_command(scope,
  operation, events, command, expected_version)` —— 操作更新 + 领域事件 +
  Outbox 行，一个事务。
- `CaseRepository.create_case_with_event_and_command(scope, case, event,
  command)` 与 `update_case_with_event_and_command(scope, case, event,
  command, expected_version)` —— 工单写入 + 事件 + Outbox 行，一个事务。

任何失败（乐观锁冲突、唯一约束、CHECK 违规）都整体回滚。在获取任何连接
或开启事务之前，每个原子方法都验证领域对象、其事件与命令描述的是同一
聚合 —— 只依据类型化标识，绝不依据 display 文案。命令信封先从其序列化
形式重新验证（`model_dump` → `model_validate`），使 `model_copy` 篡改的
实例无法绕过 Envelope 校验器；重验证失败抛出
`ValueError("command envelope is invalid")`，原始 `ValidationError` 通过
`__cause__` 保留：

- 订单操作：`operation.status == 'queued'`、`operation.version ==
  expected_version + 1`、`command.aggregate_type == 'order_operation'`、
  `command.aggregate_id == operation.operation_id`、
  `command.tenant_id / customer_id / source_message_id` 与操作一致、
  `command.expected_order_version == operation.order_version`、
  `command.payload.order_id == operation.order_id`、
  `command.payload.operation_type == operation.operation_type`，且每个
  事件的 `operation_id` / `tenant_id` / `customer_id` 一致。
- 配送调查工单：`case.case_type == 'delivery_investigation'` 且
  `order_id` 非空、`command.command_type == 'delivery_investigation'`、
  `command.aggregate_type == 'support_case'`、
  `command.aggregate_id == case.case_id`、`tenant_id` / `customer_id` /
  `source_message_id` 一致、`expected_order_version is None`、
  `command.payload.order_id == case.order_id`，且事件的 `case_id` /
  `tenant_id` / `customer_id` 一致。

命令通过
cursor-scoped helper `insert_outbox_message` 从已验证的
`ProviderCommandEnvelope` 写入；v0.7 所有命令的 capability 统一推导为
`order_operation`。`payload` 只存强类型命令 payload，可检索的 Envelope
元数据全部使用独立列；读取 Outbox 行时用 `to_envelope()` 重建
`ProviderCommandEnvelope` 并再次经过 Pydantic 验证。

保留现有不带 Command 的 Repository 方法，Graph 与现有测试不受影响。

## Inbox event_id：精确重放与冲突

`receive_inbox_idempotently` 保留唯一约束
`(provider_connection_id, event_id)`，使用 `ON CONFLICT DO NOTHING` 插入，
并发安全。插入命中既有行时，将存储记录与请求在所有可信字段上确定性比较：
`provider_connection_id`、`event_id`、`tenant_id`、`schema_version`、
`event_type`、`command_id`、`aggregate_type`、`aggregate_id`、
`raw_body_sha256` 与规范化类型化 payload。

- 全部一致 → **精确重放**：返回原有 `InboxMessage`，不创建第二条记录。
- 任一不同 → 抛出 `InboxEventConflictError`，原记录绝不被覆盖。异常消息
  只列出冲突字段名，绝不包含 raw body、签名、secret 或完整 payload。

## 7. 配送调查唯一规则

单一 active 唯一索引被替换为两个部分索引：

- 普通工单：`(tenant_id, thread_id, case_type)`，条件
  `status IN ('open','in_progress','on_hold')` 且
  `case_type <> 'delivery_investigation'`
- 配送调查：`(tenant_id, thread_id, case_type, order_id)`，条件
  `status IN ('open','in_progress','on_hold')` 且
  `case_type = 'delivery_investigation'`

`delivery_investigation` 必须有非空 `order_id`（DB CHECK + 模型校验）。
`find_unresolved_case` 增加 `order_id` 参数，CaseService 对配送调查传入
`trigger.order_id`：同一 thread 不同订单创建不同的调查工单，其他工单类型
保持原来的 thread + type 复用。

活跃订单操作唯一性按 tenant 隔离：部分唯一索引为
`(tenant_id, order_id)`，条件 `status IN ('pending_confirmation','queued',
'submitted','processing','manual_review')` —— 不同 tenant 可以使用相同
`order_id`，同一 tenant 每个订单只能有一个活跃操作；
`customer_id` 刻意不进入唯一键。终态操作（completed / rejected /
cancelled）永远不会阻止新的活跃操作。

## 8. Redrive 保持 Provider 幂等

`redrive_dead_outbox` 只接受 `dead` 消息，单事务内：`delivery_cycle + 1`、
`attempts_in_cycle = 0`、`available_at = clock_timestamp()`、清除
`dead_at` 与旧 lease —— **保持原始 `idempotency_key` 不变**，Provider
仍按同一稳定键去重。写入不可变的 `outbox_redrives` 记录；
`(tenant_id, request_id)` 唯一约束拒绝重复请求
（`DuplicateRedriveRequestError`）。本步骤不实现 HTTP API。

## 9. 刻意不公开的 API

- 不提供 `mark_outbox_published`、`mark_inbox_processed` 之类的独立
  Repository 方法：凡是同时更新领域聚合的收尾操作，未来事务协调器必须
  使用 `agent/integrations/postgres_writes.py` 的 cursor-scoped helper
  （`insert_outbox_message`、`update_outbox_transition`、
  `finish_delivery_attempt`、`mark_inbox_processed`、
  `finish_inbox_attempt`、`mark_inbox_failed`、`schedule_inbox_retry`）
  与聚合更新放在同一事务组合。
- helper 不自行获取连接、不开启事务，不通过 `agent.integrations` 或
  Graph 暴露。
- 没有 Worker 主循环、HTTP Adapter、Simulator、Webhook route、redrive
  API 或清理定时任务。

## 10. 数据保留策略（只记录，不实现）

| 数据 | 保留期 |

## 11. 领域调整

- `OperationRecordStatus` 增加 `queued`：`pending_confirmation → queued`、
  `queued → submitted | manual_review | rejected`（兼容保留
  `pending_confirmation → submitted`）。`queued` 已加入 active 状态集合、
  部分唯一索引 `uq_order_operations_active_order`、Repository 查询、测试
  Fake 与 Service 状态映射。Graph 本步骤不开始使用 `queued`。
- `CaseEventType` 增加 `provider_update`；`SupportCaseEvent` 增加
  `provider_command_id`、`provider_command_status`
  （`ProviderCommandExecutionStatus`）、`provider_reference`。
  `provider_update` 事件必须有 command id、状态与 actor（如 `system`），
  不得携带 `previous_status`/`current_status`，绝不修改 `CaseStatus`，
  绝不自动 resolved。
- `HandoffReason` 增加 `provider_delivery_failed`（Python Literal 与两个
  reason-code CHECK 同步）。

## 12. 第三步如何消费

未来 Worker：`claim_due_outbox` → `to_envelope()` 重建 Envelope → 通过
Adapter 投递 → 在单事务中组合领域更新、领域事件、`finish_delivery_attempt`
与 `update_outbox_transition`（published / dead / retry_scheduled）。
Inbox 侧：`receive_inbox_idempotently`（route）、`claim_due_inbox`、对照
本地 Outbox Command 重新验证 `command_id` / `provider_connection_id` /
`tenant_id` / `aggregate_type` / `aggregate_id`，再原子组合聚合更新 +
`mark_inbox_processed` + `finish_inbox_attempt`；`provider_update` 事件只
追加到 `support_case`。启动时运行 `recover_expired_*`；`renew_outbox_lease`
/ `renew_inbox_lease` 负责续租。
