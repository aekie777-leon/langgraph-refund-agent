# v0.7 Step 1 — Provider contract, integration domain models, reliability rules

Status: implemented in `src/agent/integrations/`.

This document records the evolution continuity of the v0.7 provider
integration. Step 1 establishes stable contracts and deterministic models
only; the HTTP adapter, outbox/inbox tables, worker, simulator, and webhook
route are later steps.

## Stable now

- Tenant and customer ownership semantics (`tenant_id` / `customer_id`,
  `AccessScope`, order ownership checks from v0.6)
- Command envelope semantics: `command_id` is the command / outbox-message
  identifier; `source_message_id` is the triggering chat message identifier;
  `aggregate_id` is a UUID identifying either an `order_operation` (the local
  `operation_id`) or a `support_case` (the delivery-investigation `case_id`)
- Provider command idempotency keys, stably bound to the aggregate:
  `order-operation:{operation_id}` and `delivery-investigation:{case_id}`
- Canonical command model: `ProviderCommandEnvelope` /
  `OrderOperationCommandPayload` / `DeliveryInvestigationCommandPayload`,
  with `schema_version` fixed to `1` and all timestamps normalized to UTC
- At-least-once delivery semantics (provider deduplicates on idempotency key)
- Command-level webhook events: `provider_command_status_changed` carries
  `command_id` plus `aggregate_type` / `aggregate_id`, the same association as
  the outbound envelope; `order_id` is auxiliary only and never used for
  authorization or unique association
- Status vocabularies are split: `ProviderCommandAcceptanceStatus`
  (`accepted` / `rejected`) for the immediate HTTP response, and
  `ProviderCommandExecutionStatus`
  (`accepted` / `processing` / `completed` / `rejected`) for asynchronous
  webhook progress, with a deterministic mapping to the local
  `OperationRecordStatus`
- Outbound API authentication (`ProviderAuthentication`) and inbound webhook
  signing secrets (`ProviderWebhookConnection`) are separate models

## Command envelope and aggregates

| Command type | Aggregate | `aggregate_id` | `expected_order_version` | Idempotency key |
| --- | --- | --- | --- | --- |
| `cancel_order` / `return_order` / `exchange_order` | `order_operation` | local `operation_id` | required (>= 1) | `order-operation:{operation_id}` |
| `delivery_investigation` | `support_case` | delivery-investigation `case_id` | must be None | `delivery-investigation:{case_id}` |

The builders are `for_order_operation` (takes a persisted `OrderOperation`)
and `for_delivery_investigation` (takes a persisted `delivery_investigation`
`SupportCase` plus the validated `issue_type`; no fake order operation is
constructed).

## Replaceable later

- HTTP Adapter (future `OrderCommandAdapter` implementation)
- `ProviderConnectionResolver` / `ProviderWebhookConnectionResolver`
  implementations (both resolvers are async protocols)
- Secret source (today a `SecretStr` in configuration; later a secret manager)
- Worker scheduling (today PostgreSQL task infrastructure; the retry and
  status rules stay)
- Provider Simulator (local development tool)

## Temporary by design

- `DemoOrderProvider` (process-local demo data; tests may keep an in-memory
  fake provider, but the production path will not use it)
- `DemoIdentityProvider` (local demo authentication)
- Environment-variable provider configuration (later replaced by a resolver)
- PostgreSQL as task-scheduling infrastructure (later a real queue may be
  introduced without changing the domain models)

## Next-version extension path

- New providers are added by implementing `OrderQueryProvider` /
  `OrderCommandAdapter`, not by changing graph logic
- Refunds and customer-service CRM integration add new webhook event types and
  command types without changing the envelope
- Secret managers plug in through `ProviderConnectionResolver`
  implementations
- Distributed rate limiting can be layered on `requests_per_second` without
  changing the domain models

## Provider boundary (transitional)

`OrderQueryProvider` (synchronous reads) and `OrderCommandAdapter` (provider
command submission) are the v0.7 core boundaries. `OrderProvider` remains as a
composition of both purely to keep v0.6 graph/service/fake code working; it is
marked transitional and will be removed once the outbox/worker command path
lands. The LangGraph layer must not depend on `OrderCommandAdapter` directly
in the long term.

## Canonical signing payload

```
{timestamp}.{event_id}.{raw_body_bytes}
```

- `timestamp`: UTC, format `%Y-%m-%dT%H:%M:%SZ` (second precision, trailing Z)
- `event_id`: the raw event identifier string (must be non-blank)
- `raw_body_bytes`: the exact request body as received (never parsed and
  re-serialized)
- Signature: lowercase hex HMAC-SHA256 over the shared secret; exactly 64
  lowercase hex characters
- Verification: recompute the digest and compare with `hmac.compare_digest`
  (constant time); reject timestamps outside the validity window; empty
  secrets, blank event IDs, and non-positive windows raise ValueError

## Webhook trust boundary

`POST /webhooks/providers/{provider_connection_id}` (future route) resolves
the trusted tenant and signing secret through
`ProviderWebhookConnectionResolver` by `provider_connection_id` only; the
tenant is never taken from the webhook body. The inbound connection
(`ProviderWebhookConnection`) carries the signing secret as a `SecretStr` and
never exposes it in repr, str, dumps, JSON, or error messages.

### Inbox processing principles

1. Query the local Outbox command by `command_id`
2. Verify `provider_connection_id`
3. Verify `tenant_id`
4. Verify `aggregate_type` and `aggregate_id` against the local command
5. Only after verification succeeds, update the business aggregate
6. Never trust aggregate ownership information carried in the webhook body

The delivery-investigation webhook only associates the `support_case` and
appends an event; whether to auto-complete or close the case is deliberately
not decided in this step.

## Retry rules

| Failure kind | Retryable | Notes |
| --- | --- | --- |
| `network_error` | yes | explicit `ProviderConnectionError` |
| `timeout` | yes | explicit `ProviderTimeoutError` |
| `http_retryable` | yes | HTTP 408, 429, 5xx |
| `http_client_error` | no | other HTTP 4xx |
| `provider_rejection` | no | explicit `ProviderRejectionError` |
| `validation_error` | no | local model/business validation |

- Classification uses explicit provider exception types only; arbitrary
  `OSError` subclasses (for example `FileNotFoundError`) are never treated as
  network failures
- Exponential backoff: `base * multiplier ** (attempts - 1)`, base 1s, ×2
- Max 8 delivery attempts; the 8th failure ends retries (`exhausted`)
- `Retry-After` honored: delay is at least the provider hint
- `max_delay_seconds` caps the backoff (including jitter); Retry-After still
  wins as a minimum delay
- Jitter only with an injected random source returning values in `[0, 1)`
  (deterministic tests)
- No sleep, no I/O in this module

## Delivery and processing statuses

Outbox: `pending → processing → published | dead` (processing also leads to
`retry_scheduled → processing`); business state never contains worker states
such as `dispatching`. Inbox: `received → processing → processed | failed`
(`failed → processing` for a manual re-drive). These are vocabulary and
transition maps only; no migration exists yet in step 1.

# v0.7 第一步 — Provider 契约、集成领域模型与可靠性规则

状态：已实现于 `src/agent/integrations/`。

本步骤只建立稳定契约与确定性模型；HTTP Adapter、Outbox/Inbox 表、Worker、
Simulator 和 Webhook 路由属于后续步骤。

## 现在稳定

- 租户与客户归属语义（v0.6 的 `tenant_id` / `customer_id` / `AccessScope` /
  订单归属校验）
- 命令信封语义：`command_id` 是命令 / Outbox 消息 ID；`source_message_id`
  是触发聊天消息 ID；`aggregate_id` 是 UUID，标识 `order_operation`（本地
  `operation_id`）或 `support_case`（配送调查的 `case_id`）
- Provider 命令幂等键：稳定绑定聚合，
  `order-operation:{operation_id}` 与 `delivery-investigation:{case_id}`
- 规范化命令模型：`ProviderCommandEnvelope` /
  `OrderOperationCommandPayload` / `DeliveryInvestigationCommandPayload`，
  `schema_version` 固定为 `1`，所有时间标准化为 UTC
- At-least-once 投递语义（Provider 依据幂等键去重）
- 命令级 Webhook 事件：`provider_command_status_changed` 携带 `command_id`
  以及 `aggregate_type` / `aggregate_id`，与出站信封使用相同的聚合关联；
  `order_id` 仅作辅助业务信息，绝不用于授权或唯一关联
- 状态词汇拆分：`ProviderCommandAcceptanceStatus`
  （`accepted` / `rejected`）用于即时 HTTP 返回，
  `ProviderCommandExecutionStatus`
  （`accepted` / `processing` / `completed` / `rejected`）用于异步 Webhook
  进度，并提供到本地 `OperationRecordStatus` 的确定性映射
- 出站 API 认证（`ProviderAuthentication`）与入站 Webhook 签名密钥
  （`ProviderWebhookConnection`）是分离的模型

## 命令信封与聚合

| 命令类型 | 聚合 | `aggregate_id` | `expected_order_version` | 幂等键 |
| --- | --- | --- | --- | --- |
| `cancel_order` / `return_order` / `exchange_order` | `order_operation` | 本地 `operation_id` | 必填（>= 1） | `order-operation:{operation_id}` |
| `delivery_investigation` | `support_case` | 配送调查 `case_id` | 必须为 None | `delivery-investigation:{case_id}` |

Builder 为 `for_order_operation`（接收持久化的 `OrderOperation`）与
`for_delivery_investigation`（接收持久化的 `delivery_investigation`
`SupportCase` 及经过验证的 `issue_type`；不会伪造订单操作）。

## 后续可替换

- HTTP Adapter（未来 `OrderCommandAdapter` 的实现）
- `ProviderConnectionResolver` / `ProviderWebhookConnectionResolver` 实现
  （两个 Resolver 均为 async Protocol）
- Secret 来源（当前为配置中的 `SecretStr`，未来接入 Secret Manager）
- Worker 调度方式（当前以 PostgreSQL 作为任务基础设施；重试与状态规则不变）
- Provider Simulator（本地开发工具）

## 有意保留的临时实现

- `DemoOrderProvider`（进程内演示数据；测试可继续使用内存 Fake Provider，
  但正式运行路径不再使用它）
- `DemoIdentityProvider`（本地演示认证）
- 环境变量 Provider 配置（后续由 Resolver 取代）
- 以 PostgreSQL 作为任务调度基础设施（后续引入真实队列时无需改动领域模型）

## 后续版本扩展路径

- 新 Provider 通过实现 `OrderQueryProvider` / `OrderCommandAdapter` 接入，
  不修改 Graph 逻辑
- 退款与客服 CRM 通过新增 Webhook event type / command type 扩展，不改信封
- Secret Manager 通过 `ProviderConnectionResolver` 实现接入
- 分布式限流可基于 `requests_per_second` 叠加，不修改领域模型

## Provider 边界（过渡期）

`OrderQueryProvider`（同步读取）与 `OrderCommandAdapter`（Provider 命令
提交）是 v0.7 的核心边界。`OrderProvider` 只是二者的组合，用于让 v0.6 的
Graph / Service / Fake 保持可用；它被明确标注为过渡兼容边界，待 Outbox /
Worker 命令路径落地后移除。长期而言，LangGraph 不应直接依赖
`OrderCommandAdapter`。

## 规范化签名载荷

```
{timestamp}.{event_id}.{raw_body_bytes}
```

- `timestamp`：UTC，格式 `%Y-%m-%dT%H:%M:%SZ`（秒级精度，末尾 Z）
- `event_id`：原始事件标识字符串（必须非空白）
- `raw_body_bytes`：按收到时的原始请求体字节（绝不先解析再重新序列化）
- 签名：对共享 secret 计算 HMAC-SHA256 的小写十六进制摘要，恰好 64 位
  小写十六进制字符
- 验签：重新计算摘要并用 `hmac.compare_digest` 恒定时间比较；超出有效期
  窗口拒绝；空 secret、空白 event_id、非正窗口抛 ValueError

## Webhook 信任边界

`POST /webhooks/providers/{provider_connection_id}`（未来路由）只通过
`ProviderWebhookConnectionResolver` 按 `provider_connection_id` 解析可信的
tenant 与签名 secret；tenant 绝不取自 Webhook 请求体。入站连接
（`ProviderWebhookConnection`）以 `SecretStr` 承载签名 secret，不出现在
repr、str、dump、JSON 或错误消息中。

### Inbox 处理原则

1. 通过 `command_id` 查询本地 Outbox Command
2. 验证 `provider_connection_id`
3. 验证 `tenant_id`
4. 对照本地 Command 验证 `aggregate_type` 和 `aggregate_id`
5. 全部验证成功后才更新业务聚合
6. 绝不直接信任 Webhook Body 中的聚合归属信息

配送调查 Webhook 只负责关联 `support_case` 并追加事件；是否自动完成或关闭
工单在本步骤不做出决定。

## 重试规则

| 失败分类 | 可重试 | 说明 |
| --- | --- | --- |
| `network_error` | 是 | 显式 `ProviderConnectionError` |
| `timeout` | 是 | 显式 `ProviderTimeoutError` |
| `http_retryable` | 是 | HTTP 408、429、5xx |
| `http_client_error` | 否 | 其他 HTTP 4xx |
| `provider_rejection` | 否 | 显式 `ProviderRejectionError` |
| `validation_error` | 否 | 本地模型或业务校验失败 |

- 分类只识别显式 Provider 异常类型；任意 `OSError` 子类（例如
  `FileNotFoundError`）绝不当作网络失败
- 指数退避：`base * multiplier ** (attempts - 1)`，基数 1 秒，×2
- 最多 8 次投递；第 8 次失败后终止（`exhausted`）
- 支持 `Retry-After`：延迟至少不低于 Provider 提示
- `max_delay_seconds` 上限作用于退避（含抖动）；Retry-After 仍作为最小
  延迟优先
- 抖动仅在注入返回 `[0, 1)` 的随机源时生效（保证测试确定性）
- 本模块不 sleep、不执行 I/O

## 投递与处理状态

Outbox：`pending → processing → published | dead`（processing 也可进入
`retry_scheduled → processing`）；业务状态绝不包含 `dispatching` 之类的
Worker 内部状态。Inbox：`received → processing → processed | failed`
（`failed → processing` 表示手动重新驱动）。本步骤只定义状态词汇与转换
规则，不编写 migration。
