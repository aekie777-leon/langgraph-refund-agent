# v1.0 observability and fault demo

Delivery Step 3 adds a bounded operational evidence path for the portfolio
showcase. It demonstrates a real transient Provider failure, the existing
Outbox retry policy, successful delivery, signed callback ingestion, and Inbox
processing without introducing a hosted monitoring service or changing domain
transactions.

## Demonstration path

Use the prepared **Retry & recovery** scenario with `ORD-10012`:

```text
Graph confirmation
  -> transactional order operation + Outbox command
  -> local Provider returns HTTP 500 on attempt 1
  -> existing Worker classifies http_retryable
  -> PostgreSQL attempt = retry_scheduled
  -> existing exponential retry becomes due
  -> local Provider accepts attempt 2
  -> Outbox attempt = accepted / message = published
  -> canonical signed callback
  -> Inbox attempt = processed
```

The failure is selected only by the development-only Showcase Provider adapter
for the synthetic order. Production `CanonicalHttpProviderTransport`, retry
classification, attempt limits, leases, fencing, finalizers, Graph policy, and
wire schemas are unchanged.

## Payload-free activity API

An authenticated Supervisor can read:

```http
GET /internal/provider-operations/attempts?limit=50
Authorization: Bearer <supervisor-token>
```

The endpoint requires the existing exact `supervisor` role and
`provider_ops:read` permission at both Service and PostgreSQL boundaries. The
tenant comes only from the verified `AccessScope`; callers cannot provide it in
the path, query, headers, or body.

Each result contains only:

- queue (`outbox` or `inbox`), resource ID, and command ID;
- delivery/processing cycle and attempt number;
- structured outcome, allowlisted failure kind, HTTP status, and sanitized
  error code when applicable;
- attempt start and finish timestamps.

The query is bounded to `1..100`, orders newest attempts first, and joins every
attempt through its tenant-scoped queue record. It never projects payloads,
customer/source-message identity, worker or lease IDs, Provider connection or
operation references, callback hashes, raw errors, credentials, or signing
material.

## Console evidence

The Provider Ops workspace loads the existing queue overview and recent
attempt activity concurrently. The timeline makes the historical
`retry_scheduled`, `accepted`, and `processed` outcomes visible even after the
queues reach their final states. Customer and support-agent personas continue
to receive the normal authorization failure.

To run the local stack:

```powershell
docker compose --env-file .env.showcase -f compose.yaml -f compose.showcase.yaml up --build -d
```

Then:

1. select **Retry & recovery** as Maya;
2. run the Graph and confirm the operation;
3. switch to Sam, open **Provider Ops**, and refresh queues;
4. inspect the retry and recovery attempts without exposing business payloads.

## Operational interpretation

This implementation shows that failures are explicit, classified, persisted,
recoverable, tenant-scoped, and reviewable. It is intentionally not a complete
production observability platform. It does not add Prometheus/OpenTelemetry,
distributed tracing, Worker heartbeat persistence, alert delivery, retention
cleanup, or a hosted dashboard. Those would require separate capacity,
retention, privacy, and deployment decisions.
