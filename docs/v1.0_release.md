# v1.0 portfolio release

Version 1.0 turns the existing refund-agent backend into a reviewable GitHub
portfolio project. It does not replace the production identity and reliability
boundaries built through v0.9; it makes those boundaries runnable, observable,
and easy to evaluate without cloud credentials.

## What a reviewer can verify

| Review goal | Fastest evidence path |
|---|---|
| See the product | Start the [local showcase](v1.0_showcase.md) and open the React console |
| Inspect agent control | Run a prepared scenario and observe the real LangGraph interrupt before a write |
| Inspect AI safety | Review the [evaluation dataset and report](v1.0_evaluation.md) |
| Inspect failure handling | Run the [Provider retry and recovery demo](v1.0_observability.md) |
| Inspect authorization | Switch customer, support-agent, and supervisor personas in the console |
| Inspect persistence | Follow Case events and payload-free Provider attempt history from PostgreSQL |

The demonstration uses deterministic model-facing adapters so that the Graph,
policy, persistence, authentication, and worker paths can be reviewed without
an API key, network model call, or variable model output.

## Release architecture

The v1.0 portfolio layer adds three replaceable surfaces around the established
application:

- a React/TypeScript console that calls only public LangGraph and scoped
  internal FastAPI contracts;
- deterministic showcase adapters selected only by an explicit development
  profile;
- versioned evaluation and operational evidence that reuse production routing,
  retry, RBAC, tenant, and persistence code.

The following boundaries remain unchanged:

- the LangGraph node/edge topology and human confirmation behavior;
- deterministic refund, handoff, assignment, and Provider policies;
- Provider command and callback wire contracts;
- migrations `0001` through `0008` and v0.9 data compatibility;
- production OIDC/JWKS, SCIM, tenant, RBAC, audit, and fail-closed startup
  requirements.

## Release verification

The repository's release matrix covers:

- Ruff, mypy, package build, frozen dependency resolution, and the complete
  pytest suite on Python 3.11 and 3.12;
- disposable PostgreSQL integration tests for ownership, identity, Cases,
  Outbox/Inbox, Provider operations, retries, fencing, and concurrency;
- deterministic regeneration and byte-for-byte verification of the committed
  AI evaluation JSON evidence;
- ESLint, Vitest, TypeScript, and Vite production build for the console;
- Playwright against the local Compose stack for Graph interrupt/resume,
  assignment authorization, and persisted Provider failure/recovery;
- Compose configuration, image startup, package contents, whitespace, and
  secret-pattern checks during release closure.

CI intentionally does not call a hosted model, mutate an IdP or SCIM tenant,
deploy infrastructure, or contact production systems.

## Compatibility and data impact

v1.0 has no new database migration. Existing v0.9 records, identity keys,
canonical actors, API clients, Provider messages, and worker state remain
compatible. The new Provider attempt endpoint is additive, read-only,
Supervisor-only, bounded, tenant-scoped, and payload-free.

Rollback removes the showcase UI and development adapters without requiring a
data rollback. Operators must still coordinate Worker versions according to
the existing v0.8 redrive compatibility contract.

## Honest limitations

This release is a portfolio demonstration, not a production deployment. It
does not include real customer data, hosted model evaluation, production
secrets, cloud infrastructure, alert delivery, OpenTelemetry/Prometheus,
worker heartbeat persistence, retention automation, a distributed rate
limiter, external queue infrastructure, or dynamic Provider secret rotation.

The local Compose PostgreSQL, Redis, demo Bearer tokens, deterministic model
adapters, and Provider simulator are development-only. Production still
requires an approved IdP and directory, external TLS PostgreSQL, gateway
controls, managed secrets, operational monitoring, privacy/retention policy,
capacity testing, and organization-specific safety/legal review.

## Release ownership

Technical validation does not create a GitHub release or approve production
use. The repository owner retains control of commit, tag, push, release notes,
and any future deployment. The intended tag after final acceptance is
`v1.0.0`.
