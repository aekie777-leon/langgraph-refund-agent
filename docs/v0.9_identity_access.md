# v0.9 Production Identity and Access Boundary

Version 0.9.0 establishes the production authentication and personnel-lifecycle
contract shared by the custom FastAPI routes and LangGraph Server. It defines a
deployable envelope but does not deploy infrastructure, connect to a real IdP or
SCIM tenant, or include production credentials.

## Runtime boundary

Both HTTP surfaces resolve the original `Authorization: Bearer` value through
one process-wide async identity runtime. The application never trusts unsigned
forwarded user, tenant, role, permission, or group headers from a gateway.

Production requires:

- one trusted OIDC issuer and audience;
- an explicit asymmetric JWT algorithm allowlist;
- stable application-specific user, tenant, and groups claims;
- an allowlisted external-group-to-role mapping;
- one read-only SCIM 2.0 directory;
- an external PostgreSQL service with TLS enabled; and
- `langgraph.json`, where `disable_studio_auth=true` routes Studio requests
  through the same custom authentication boundary.

`langgraph.dev.json` is the explicit local Studio profile. It is excluded from
the production image. `DemoIdentityProvider` and local Compose PostgreSQL are
temporary development/test implementations and production mode rejects them.

## Token verification

The OIDC adapter locally verifies JWT signatures and requires `iss`, `aud`,
`exp`, `nbf`, `iat`, and `kid`. Issuer, audience, and algorithms are fixed
configuration, not token-selected policy. Only configured user, tenant, and
groups claims are consumed. A token containing a `permissions` claim is
rejected; application permissions are always derived from backend RBAC.

JWKS responses are size- and key-count-bounded. A known key remains usable
within its TTL without an online IdP request. An unknown `kid` causes at most
one forced refresh for that resolution attempt. Concurrent refreshes are
coalesced. Once the cache is expired, an unavailable or malformed JWKS endpoint
fails closed. Invalid credentials return 401; identity infrastructure failures
return 503. Neither response includes claims, token contents, keys, URLs, or
upstream response details.

## Claim and audit policy

Configure app-specific identity claims whose values satisfy the existing
`tenant_id:user_id` actor-key constraints. Role comes only from the configured,
non-overlapping group mapping. Multi-issuer federation and direct `sub` mapping
are deferred because they require an identity registry and migration decision.

Raw access tokens, complete claims, JWKS documents, and external-directory
payloads are neither logged nor persisted. Existing audit records continue to
store only the canonical `tenant_id:user_id` actor.

## SCIM assignment policy

The directory adapter makes read-only `GET` requests to `/Users`, projecting
only the configured user ID, tenant ID, active flag, and roles attributes. It
uses an exact tenant-and-user filter and requests at most two results. Startup
preflight uses read-only `GET /ServiceProviderConfig`.

For a new assignment, the service first resolves the Case inside the caller's
tenant scope, then checks the target. The target must be:

- an exact user and tenant match;
- active; and
- mapped to `support_agent` or `supervisor`.

Missing, mismatched/cross-tenant, inactive, and wrong-role targets return the
same safe 404 result. Malformed, ambiguous, unavailable, or oversized SCIM
responses return 503. Every failure occurs before a Case or Event write.
Successful idempotent replay uses the stored event and does not depend on a new
directory lookup.

## Production configuration

The complete variable list and safe empty placeholders are in `.env.example`.
Production must set at least:

```text
APP_ENV=production
IDENTITY_PROVIDER=oidc
IDENTITY_DIRECTORY=scim
OIDC_ISSUER=https://...
OIDC_AUDIENCE=...
OIDC_JWKS_URL=https://...
OIDC_ALLOWED_ALGORITHMS=RS256
OIDC_USER_ID_CLAIM=...
OIDC_TENANT_ID_CLAIM=...
OIDC_GROUPS_CLAIM=...
OIDC_ROLE_GROUPS_JSON=...
SCIM_BASE_URL=https://...
SCIM_BEARER_TOKEN=<secret-manager reference or injected value>
SCIM_USER_ID_ATTRIBUTE=...
SCIM_TENANT_ID_ATTRIBUTE=...
SCIM_ACTIVE_ATTRIBUTE=active
SCIM_ROLES_ATTRIBUTE=roles
SCIM_ROLE_MAPPING_JSON=...
POSTGRES_URI=postgresql://...?...sslmode=verify-full
PROVIDER_ALLOW_INSECURE_HTTP=false
```

Production accepts only `POSTGRES_URI`; component-based database assembly is a
development convenience. The URI must name a non-local host and use
`sslmode=require`, `verify-ca`, or `verify-full`. `verify-full` is recommended.
PostgreSQL credentials and CA material must be injected by the deployment
platform and never baked into the image.

The process publishes its server health only after OIDC JWKS and SCIM preflight,
PostgreSQL pool readiness, and application dependency configuration complete.
A missing setting, demo backend, Studio bypass, unreachable identity service,
or database startup failure prevents successful startup. Gate traffic on the
Agent Server `/ok` health result; do not treat container creation or TCP accept
alone as readiness.

## Gateway contract

The repository intentionally does not bind to a gateway product. A production
gateway must:

- terminate externally trusted TLS and use protected upstream networking;
- pass the original Bearer token to the application;
- enforce request-size, timeout, and rate limits appropriate to each route;
- redact Authorization, cookies, tokens, signatures, claim values, SCIM
  payloads, query filters, and secret-bearing configuration from logs; and
- keep internal Case, Provider Ops, webhook, Studio, and health exposure within
  reviewed network policy.

Gateway-authenticated identity headers cannot replace application JWT
verification in v0.9. Provider connections must use HTTPS in production.

## Rollout and rollback

There is no migration 0009. Data written by v0.9 remains compatible with the
v0.8 schema and API. Apply existing migrations 0001-0008 before starting the
service, configure the external dependencies, then require a successful
preflight and `/ok` result before routing traffic.

Do not run v0.8 and v0.9 API instances as one trusted production identity pool:
v0.8 can still use demo auth and does not enforce SCIM assignment eligibility.
Drain old API instances before declaring the v0.9 boundary active. A code
rollback needs no database rollback, but it removes the new authentication and
assignment guarantees; disable production traffic or restore a separately
reviewed equivalent boundary before starting v0.8 code. Preserve all Case and
Event audit records.

## Verification

All external tests use controlled local HTTP fakes and disposable PostgreSQL.
They do not access or mutate production systems. The closure matrix is:

```bash
uv sync --frozen --extra dev
uv run ruff check .
uv run mypy src
uv run pytest -m "not postgres" -p no:cacheprovider
CASE_TEST_POSTGRES_URI=<disposable-uri> uv run pytest -m postgres -p no:cacheprovider
uv build
docker compose config --quiet
```

The cross-component identity acceptance test is
`tests/integration_tests/test_identity_access_e2e.py`.

## Deferred scope

v0.9 does not include a management UI, retention cleanup, Worker heartbeat or
Prometheus metrics, a distributed limiter/external queue, dynamic Provider
secret rotation, multi-issuer federation, tenant self-service claim mapping,
multi-architecture images, a hardened PostgreSQL image, or a real production
deployment. Production observability and data lifecycle are the recommended
v1.0 focus.
